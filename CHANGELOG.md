## Текущий milestone

**Build 85.60-file-base** — БАЗА БОЕВЫХ СТАТОВ БЕРЁТСЯ ИЗ ФАЙЛОВ ИГРЫ (РЕШЕНИЕ ВЛАДЕЛЬЦА).

«Можно брать базу из файлов игры и множить их. Так надёжно» — так и сделано. Гадания в этом
месте больше нет: `src/runtime/EnemyFileBase.h` — таблица на 91 вид, **сгенерированная** из
`enemies.zip` (charparam/em/*_cmn.prp, смещения 0x0C64/0x0C6C/0x0C74/0x0C7C) командой
`python3 tools/charparam_dump.py --codegen`. Умножение (`attackMult` и прочее) работает как
работало — изменился только источник базы.

**Почему это лечит.** Старый код угадывал базу по абсолютному порогу («выше 350 — значит наша
прошлая запись, делим»), а числа видов различаются в сорок раз: однажды это поделило уже
изменённое значение и вид получил вдвое слабые статы (85.58, гоблин 126.2 вместо 250). Теперь
база — из данных, а два аварийных пути (таблица видов из памяти, затем оценка) остались только
для видов, которых в таблице нет или у которых в файле стоят не боевые числа.

**Отсев.** Годными считаются базы, где все четыре поля > 0 и < 9000. Так отсеиваются нули
(em1200/em1201/em6003) и «иммунные» круглые маркеры (em5100 mdef 10000, em5101 def 10000/
mdef 20000), но сохраняются настоящие крупные бойцы: у em7001 атака 8500 — реальная.

**Лог (по две строки на вид за сессию):**
```
combat base uEm0100 raw atk 400.0 ... -> base 250.0/75.0/80.0/75.0  from=FILE
combat base uEm0100 source=FILE file atk 250.0 def 75.0 matk 80.0 mdef 75.0
```
Плюс строка `RAW MISMATCH` только если прочитанное из памяти расходится с файлом больше чем на 3%
— в норме её нет.

**Фикстура `filebase_test`** (в гейте): числа гоблина совпадают с полем (250/75/80/75), хоб 410,
волк 220, харпия 350, крупный em7001 не отсеян, нули и иммунные маркеры отсеяны, дублей emId нет.
Заодно выяснилось: часть карточек лежит в нескольких папках (em5401_cmn.prp есть и в em5401/,
и в em5402/) — генератор их дедуплицирует по номеру вида.

**Ожидаемый эффект в поле:** гоблины вернутся к задуманной крепости — в прошлой сессии база была
занижена вдвое, теперь она 250, и при ×3 атака солдата выходит ~866 вместо ~437. Если покажется
много — это ручки `attackMult`/`defenseMult` в живом `ddda_entities.ini`.

## Предыдущий milestone

**Build 85.59-base-truth** — ЛИНИЯ БАЗЫ ВИДА; РАЗГАДАНА РАЗНИЦА БАЗ МЕЖДУ СЕССИЯМИ (СМОТРИ `TEST_85.59.txt`).

**Владелец ини не трогал много билдов** — значит разницу баз боевых статов между сессиями
дал не файл настроек. Разбор (полностью — `docs/COMBAT_BASE_INVESTIGATION.md`):

* в файлах игры у гоблина (`em0100_cmn.prp`) **atk 250 / def 75 / matk 80 / mdef 75**, и лог 85.57
  прочитал из памяти **ровно эти числа** — та сессия права;
* числа **126.2 нет ни в одном файле игры** (поиск по всему архиву), а `126.2 = 400 / 3.169`,
  где 3.169 = ×3 × ролл. Значит в сессии 85.58 код прочитал уже изменённое 400 и **молча поделил**
  его эвристикой «похоже на нашу запись»;
* цена: в той сессии гоблины вышли ~437 атаки вместо ~795 — примерно вдвое слабее задуманного
  (ремарка владельца «патруль вынесли относительно легко» этим и объясняется).

**Корень** — абсолютный порог (атака > 350, защита > 120) при разбросе чисел видов в сорок раз:
наша запись у гоблина за порог попадает и распознаётся верно, а любое чужое значение выше порога
тихо делится, и весь вид на сессию получает половину базы — без единой строки в логе.

**85.59**: при первом теле каждого вида печатается строка `combat base … raw … -> base … from=estimate
RECOVERED-…` плюс справочная строка из файла игры с отклонением сырого значения от файла
(`deviation raw atk x3.170`). Эвристика больше не решает молча. Инструмент для дампа карточек:
`tools/charparam_dump.py` (97 видов, `--search <число>` для проверки «а есть ли такое в данных»).

**Предложение на смену** (кода нет, нужно решение): база вида из файлов игры таблицей для
ранжируемых видов (гоблин 250/75/80/75, волк 220/60/70/100, сауриан 440/130/200/60,
харпия 350/90/160/130), эвристика — только аварийный путь для видов вне таблицы и всегда с пометкой.

## Предыдущий milestone

**Build 85.57-zone-sets** — НАБОРЫ ПАЧЕК ПО МЕСТУ: В ЭТОЙ ЗОНЕ ТАКОЙ СЕТ, В СЛЕДУЮЩЕЙ ДРУГОЙ (СМОТРИ `TEST_85.57.txt`).

**Запрос владельца.** «Если все пачки в сессии будут одинаковыми по рангам, весь смысл теряется.
Это должна быть динамичная система: в этой зоне такой сет, в следующей — другой. Менеджить и дебажить
сложнее, но по-другому никак».

**Что было не так.** Каждая особь роллила ступень независимо из общих весов, поэтому любая пачка
выглядела статистически одинаково: три-четыре новичка, четыре-пять солдат, ветеран. Разница между
пачками возникала только случайно.

**Что сделано.** У МЕСТА карты есть набор (сет) весов ступеней. Ключ места — из `ENCOUNTER_MEMORY_DESIGN`
§1: `floor(x/cell)`, `floor(z/cell)`, без высоты. Ячейка 40 м, наследование набора в радиусе 25 м
(тела рядом берут один набор — пачка не рвётся на границе ячейки). Четыре набора: `rabble` 30 %,
`patrol` 40 % (как было), `warband` 20 %, `hunt` 10 %. Набор двигает только СОСТАВ пачки: размер,
множитель атаки и крепость каждой ступени остаются в `[ranks]`.

**Заодно предел «один мини-босс на место».** До наборов двойной мини-босс был лотереей 2 %; набор
`hunt` отдаёт мини-боссу 10 % веса, и без предела это стало бы обычным делом. Лишний понижается
на ступень (элита), а не отменяется. Ключ `[packs] minibossPerPack`, 0 = без предела.

**Секция `[packs]` читается на ходу** — тот же сторож, что у `[ranks]` (85.56). Правка влияет на места
и особей, которые появятся после неё: у уже живущих ступень и набор заморожены в записи тела.

**Проверено фикстурой:** 2048 мест — все четыре набора живые, доли совпадают с весами; 256 мест по
12 тел — в 85 местах пачка почти целиком из новичков, в 74 — из ветеранов. Плюс структурная проверка:
набор спрашивается ТОЛЬКО при выдаче ступени (иначе место «переиграло» бы набор у живой особи).

## Предыдущий milestone

**Build 85.56-ranks-live** — ВЕСА РАНГОВ ЧИТАЮТСЯ НА ХОДУ; СТУПЕНЬ ПРИВЯЗАНА К СУЩЕСТВУ (СМОТРИ `TEST_85.56.txt`).

**Что попросил владелец.** «Веса — это рантайм, крутить можно на ходу». По правилам проекта рантаймом
был только `ddda_entities.ini`, а `[ranks]` в главном ини читался ровно один раз при запуске. Сами по
себе веса ни на что, кроме БУДУЩИХ особей, не влияют — значит живое чтение для них безопасно.

**Что сделано.**
1. **`[ranks]` читается на ходу.** Сторож по времени изменения файла — та же схема, что у
   `ddda_entities.ini` (не чаще 500 мс, пропуск одного цикла после правки, чтобы не прочитать
   недописанный файл). В логе видно: `Monster Director: ranks RELOADED from ini (live read, 85.56)`.
2. **Ступень выдаётся один раз и замораживается.** Это условие безопасности живого чтения: иначе
   правка весов посреди боя переобула бы ЖИВОГО монстра — поехали бы рост, множитель атаки и крепость.
   Теперь числа ступени берутся в первый тик жизни особи и живут в записи тела.
3. **Ступень привязана к существу, а не к адресу.** Поле 85.55: адрес `0x10D57470` отдал «ветерана»
   гоблину, а следом волчице в том же слоте — снова «ветерана» (вес ветерана 13%, повтор случайным быть
   почти не может). В ролл добавлено ПОКОЛЕНИЕ жильца — счётчик, растущий при смене хозяина слота.
   В строке ранга теперь видно `gen=N`, а в строке смены жильца — `(gen N)`.
4. **Строка смерти больше не печатает чужие числа.** Там же, 85.55: `rank=veteran pois 600 kdown 100
   burn 400` на умершем гоблине — это ванильные числа волка, занявшего адрес. Теперь перед печатью
   спрашиваем у живого объекта его класс: сменился — печатаем `pools=stale(now uEm0200)` вместо чисел.
   Нет числа лучше, чем чужое число.
5. **Ранг в логе больше не пересчитывается, а спрашивается у тюнера** (`RankIssuedFor`). С живым
   чтением пересчёт мог бы назвать не ту ступень, по которой особь живёт.

**Легенда сводки по огню уточнена** (полировка из повестки смены): `died` читается как «умер, пока
горел» — пешки бьют горящих, и смерть могла прийти от кинжала, а не от огня.

**Ступени урона не менялись ни на цифру:** это инфраструктура, а не баланс. Фикстура рангов расширена
(поколение жильца) и проходит; в `syntax_check.sh` добавлена структурная проверка «ролл живёт только в
выдаче ступени» — потерять её при рефакторинге легко, а в поле это выглядело бы как «монстра
переобуло в бою».

## Предыдущий milestone

**Build 85.55-burn-book** — СВОДКА ПО ОГНЮ СЧИТАЛА НЕВЕРНО; ПОЧИНЕНО (СМОТРИ `TEST_85.55.txt`).

**Поле 85.54 (21 тело: 4/11/2/0/0 + волки).** События горения появились и сработали. Но итоговая строка
соврала: `burn summary caught=7 survived=1 died=0`, тогда как **три гоблина погибли, стоя в огне**.

**Причина — наша.** Смерть в огне считалась только по признаку «имя последнего действия выглядит
смертельным» (Die/Dead). Но прибор ставит вердикт о смерти ещё и по близости («исчез рядом и только
что») — в логе такие смерти помечены `conf=likely`. У погибших в огне последним действием было
`DmgBurn`, признака смерти в нём нет, и счётчик их не видел. Исправлено: книга закрывается на настоящем
вердикте о смерти.

**Заодно счёт стал закрытым.** `BURN-SURVIVED` печатается живьём (владельцу видно в бою), но в счёт
больше не идёт: наблюдатель смотрит на особь с интервалом и переход через `DmgBurnEnd` легко
пропустить. Выживание теперь определяется по судьбе тела: погиб в огне / погиб от другого (значит
огонь пережил) / ушёл из вида. Итог: `burn summary bodies=N starts=N survived=N died=N left=N`.

**Пересчёт боя вручную (что было на самом деле):** загорелось 5 тел, 7 возгораний (двое вспыхивали
дважды); погибли в огне оба новичка (запас 300) и один солдат (405); огонь пережили двое солдат (405),
погибнув позже от других причин. Книга сходится: 5 = 3 + 2. **Первое прямое полевое подтверждение
работы ступеней**: до 85.47 запас огня у всех гоблинов был ровно 300 и в огне гибли все.

**Подготовлена повестка смены** — [`docs/SHIFT_AGENDA.md`](docs/SHIFT_AGENDA.md): очередь чистки
(главное — 512 слотов вместо 128), полировка (порядок ключей, пометка «взято умолчание», правило
безопасных умолчаний), документы (навигация по HUB, «первые шаги» в README, журнал полевых
подтверждений, единый индекс знаний) и десять тем брейншторма. Там же — ключи для честного теста
на чистом сейве: `attackMult = 1.1112` (минимум, при котором даже худший ролл 0.9 остаётся на ванили),
`defenseMult = 1.0`.

**Запись знания (30.09)** — ТРИ РАЗНЫХ СОБЫТИЯ: ПАДЕНИЕ, СТАГГЕР, ВЫДОХ.

Владелец уточнил терминологию по наблюдениям в поле («на глаз»), и это важно зафиксировать до
