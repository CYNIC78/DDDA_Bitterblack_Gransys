# Архитектура DDDA AI Overhaul

## 1. Идентичность проекта

> Замысел и направление — в [`VISION.md`](VISION.md). Здесь — устройство
> того, что уже построено.

DDDA AI Overhaul — runtime-платформа для естественного улучшения AI пешек и монстров. Мод не подменяет каждое действие и не строит параллельный игровой движок. Он меняет штатную политику выбора, а родные planner/FSM/анимации исполняют решение с учётом физической возможности.

Главное правило:

```text
Можем прочитать/изменить живой объект — делаем LIVE.
Статические ресурсы используем как CATALOG.
PACK нужен только если движок физически не может создать требуемый объект/граф.
```

## 2. Четыре слоя данных

| Слой | Назначение | Примеры |
|---|---|---|
| **LIVE** | обратимое чтение/запись процесса | priority rules, inclinations, action parameters, погода |
| **CATALOG** | офлайн-описание игровых ресурсов | TypeAtlas, `cmc.prt`, GOAP, `AIPlActParam*`, bestiary |
| **MEMORY** | наша долговременная память/профили | `ddda_pawn_ai_profiles.ini`, будущие world sidecars |
| **PACK** | редкие недостающие игровые ресурсы | LOT/GPL/ARC только после доказанного отказа LIVE |

CATALOG не заменяет игровые файлы пользователя. Он позволяет LIVE-слою находить и проверять штатные объекты.

## 3. Вертикальный AI pipeline

```text
Sensors / target candidates
  → current target selection
  → priority policy
  → selected intent/code
  → GOAP planning
  → action eligibility
  → FSM/action lifecycle
  → motion/collision/damage
```

### 3.1 Sensors и target selection

Определяют, что существует вокруг и кто является текущей целью. Ресурсы `.sn2/.stg` разобраны.

> **DEPRECATED (аудит 84.21):** «точный live current-target ещё не закреплён».
> Канон: `uCmc+0x2EB8` CONFIRMED — [`SOURCE_OF_TRUTH.md`](SOURCE_OF_TRUTH.md) §4.

### 3.2 Priority — основной слой управления

Priority отвечает: «что сейчас важнее?». Это главный продуктовый рычаг: настойчивый совет, а не принудительный запуск действия.

Для главной пешки подтверждены:

- 85 `cPrioParam` rows;
- 48 runtime buckets;
- 48 personality `cCodeParam` rules;
- 41 order rules;
- `AddS32` как целочисленное смещение live bucket;
- persistent profiles из 0..48 транзакционных entries.

Если действие невозможно, downstream-слои естественно отказывают или выбирают альтернативу.

### 3.3 GOAP — план и статические исправления

GOAP отвечает: «как достичь выбранного намерения?». Его не следует динамически переписывать каждый тик. Допустимы проверенные патчи явных дыр: неправильная premise, недостижимая цель, отсутствующий переход.

### 3.4 Action eligibility

Проверяет, можно ли использовать конкретный приём при текущем оружии, дистанции, высоте и атрибутах. `AIPlActParam*` уже каталогизированы; runtime A/B ещё впереди.

### 3.5 FSM/action

FSM управляет жизненным циклом действия (`Init/Update/Exit`, recovery, переходы). Прямую подмену current Act не используем как интеллект. FSM меняется только хирургически для исправления доказанного тупика.

## 3.6. Конвейер стороны монстров (актуально на 85.66)

Порядок, в котором мод трогает монстра, и где это лежит:

```
Runtime::World (WorldScan.cpp)      обход актёров → вид тела → списки видов
   │                                 (KindIsHarmless / KindIsStructural — одна правда)
   ▼
EnemyTuner (EnemyTuner.cpp)         для каждого тела: EnsureRankIssued →
   │   1) ступень из [ranks]         ступень выдаётся РОВНО ОДИН РАЗ на жильца
   │   2) база вида                  EnemyFileBase.h (91 вид, из файлов игры)
   │      × множитель ступени        политика полей: 0 не пишем, ≥9000 иммунитет
   │   3) размер                     полоса ступени (у волка размер выключен)
   │   4) запасы/крепость            rankNResist / rankNStand — НЕ здоровье
   ▼
MonsterAI::Director                 инстинкт стаи: приказ → адреналин (темп)
   │   + набор пачки места          [packs]: ячейка 40 м → сет (12 слотов)
   ▼
Runtime::Tempo                      множители воспроизведения (ярость/рывок)
```

Каждый шаг подписан в логе строкой, по которой видно ЧТО и ОТКУДА взято
(`from=FILE` / `from=species` / `from=estimate`, `rank … set=… gen=…`, `policy=…`).
Правило: если шаг не оставил строки, его нельзя ни подтвердить, ни опровергнуть —
поэтому «молчаливых» решений в этом конвейере не бывает.

Полная карта файлов и их ответственности — генерируемый [`CODE_MAP.md`](CODE_MAP.md).
Ключи, которыми всё это настраивается, — [`INI_REFERENCE.md`](INI_REFERENCE.md);
контракты — `SOURCE_OF_TRUTH.md` §16.

## 4. Runtime-платформа

```text
TypeAtlas + DTI discovery   = идентификация живых объектов
MemProbe / Runtime.h        = подтверждённые контракты памяти
CombatBus / CombatIntel     = события и контекст боя
Policy modules              = решение мода
Profile sidecars            = пользовательский устойчивый выбор
Native AI                   = планирование и исполнение
```

### 4.1 Никаких transient addresses на диске

После каждой загрузки объекты ищутся заново по DTI, полному identity tuple и проверяемым полям. Heap-адреса и наблюдавшиеся vtable VA одного запуска не являются профилем.

### 4.2 Транзакционные мутации

Общий контракт:

```text
resolve all
→ validate all expected fields
→ write all
→ read back all
→ monitor convergence
→ rollback all on failure/profile switch/unload
```

Ни одна частичная конфигурация не должна оставаться активной после ошибки.

### 4.3 Sidecar, а не DDDA.sav

Пользовательские профили и будущая память мира хранятся в наших файлах. Чужой save format не изменяется. Настройки игрока и состояние мира в будущем должны быть разделены.

## 4.4 Разделение продукта и исследования (Build 69)

Мод состоит из двух физически разделённых слоёв.

```text
src/runtime/     продукт: работает всегда, не знает про DevTools
src/devtools/    исследование: SCAN/DUMP/HUNT, выключается целиком
```

Правила:

1. Продуктовый код **не вызывает** функции DevTools. Единственная точка
   связи — `Runtime::ResearchHooks`: продукт объявляет места, где research
   *может* что-то сделать, а DevTools подписывается на них при инициализации.
   Панель выключена — указатели нулевые, продукт идёт дальше.
2. Обратное направление разрешено: DevTools включает `RuntimeInternal.h`
   и читает состояние продукта. Исследование смотрит на продукт, не наоборот.
3. `Runtime::Init()` вызывается из `InitHooks()` **до** инициализации UI.
   Продукт не имеет права зависеть от того, поднялся ли ImGui-оверлей.
4. Ни одна продуктовая ветка не гейтится флагом `[devtools] enabled`.

Инвариант проверяется автоматически: `tools/analyze_devtools_layers.py`
возвращает 1, если продуктовый код снова появился в `DevTools.cpp`.

## 5. Модульность

- Модули общаются через события и узкие контракты, а не читают внутренности друг друга.
- `CombatIntel` сообщает факты, но не решает поведение пешки.
- Priority controller меняет политику, но не запускает анимацию.
- GOAP/FSM patches имеют manifest/hash/rollback и не смешиваются с динамическими профилями.
- DevTools выключен по умолчанию и на продукт не влияет (Build 69).

### 5.1 Как добавить новый pawn-модуль

`src/PawnAI.cpp` — тонкий оркестратор, поведение живёт в `src/pawnai/`.
Эталон для копирования — `SmartUtilitarian.{h,cpp}`.

1. Скопировать `src/pawnai/SmartUtilitarian.{h,cpp}` → `MyModule.{h,cpp}`.
2. Добавить `#include` и поле модуля в `src/pawnai/PawnAI_BusOrchestrator.h`.
3. Добавить оба файла в `ddda-ai-overhaul.vcxproj`.

Модуль сразу слушает `CombatBus` — отдельная подписка не нужна.

Действующие модули: `PresetManager` (пресеты), `AcquisitorManager` (бывший
Sanitary Cordon; с Build 55 Guardian/Nexus из-под кордона выведены),
`SmartUtilitarian`, `TacticalSwitch`, `GuardianDoctrine`, `NexusDoctrine`.

### Nexus 85.08: границы ответственности

`NexusPolicy.h` — чистые решения (выбор угрозы, постоянный/временный якорь),
без чтения игровой памяти. `NexusDoctrine.cpp` — runtime-адаптер: snapshot партии,
CombatBus, валидация кандидатов и запись combat target. Вызывается отдельно
в `PawnAI.cpp`, а не через подписку `PawnAI_BusOrchestrator`.
Порядок: Guardian → Nexus → Rescue → OrderWatch. Активный Rescue блокирует
пин Nexus, но назначение сохраняется; полного арбитража нет.
Nexus не владеет общим tempo override и с 85.08 не пишет его или gaze.
Выход из gameplay/master OFF сбрасывает назначение. Идентичность проверяется
по слоту, телу и записи; это не поколенческий handle.
Точные условия и неподтверждённые границы: [`NEXUS_DOCTRINE.md`](NEXUS_DOCTRINE.md).
WandRange остаётся отдельным механизмом eligibility, не позиционирования.

Модуль поведения обращается к миру только через `src/runtime/Runtime.h`
(позиции, враги, Guardian-фикс). Прямые вызовы `DevTools::` запрещены.

## 6. Производительность и устойчивость

- Низкочастотная политика работает в существующем тике около 150 мс.
- Полные heap census выполняются адресно/однократно, не каждый кадр.
- Dynamic priority profile может ждать естественный think rebuild; UI показывает `PENDING/CONVERGED`.
- Запись разрешена только после exact validation.
- При неизвестном объекте/версии мод деградирует в vanilla, а не угадывает.

Цифры сняты с дерева теми же инструментами, что стоят в гейте, поэтому их можно перепроверить,

длины функций и глобальное состояние — эвристика (регексп + баланс скобок), там допустима

### 8.2 Как модуль подключён на самом деле

Планировалось «модули на шине». По факту подключение живёт на трёх уровнях, и это осознаннее
исходного замысла:

1. **Данные — по шине.** `src/CombatBus.h`: `Publish`/`LastReport` под SRWLOCK, слушатели,
   правило «кривой модуль не роняет соседа». Два канала: удар (`CombatIntel`, каждые 150 мс,
   затирает слот) и присутствие (`WorldScan`, отдельный канал) — удар не топчет картину мира.
2. **Решения — дельтами.** `src/pawnai/PawnAI_BusOrchestrator.h`: модуль НЕ пишет ползунки,
   а возвращает поправку; оркестратор складывает `anchor + Σdelta` и делает один лерп.
   Итог — модули не дерутся за один и тот же канал.
3. **Время — цепочкой.** `UpdatePawnAI()` — плоский список из 21 вызова под `__try`/`__except`,
   каждый со своим комментарием. Порядок задан явно и не выводится из графа зависимостей.

Почему это лучше полиморфной шины именно здесь: мы живём внутри чужого процесса, где главный
риск — «прочитал мусорный указатель». Предсказуемый порядок и SEH-изоляция на вызов дают больше,
чем единый интерфейс: падение одного модуля не утягивает остальные, а порядок виден в одном
экране вместо реконструкции по графу.

Цена решения: `PawnAI.cpp` тянет 25 включений и остаётся главным узлом сцепления. Первые два
уровня убирают сцепление по данным, третий — сознательно оставлен ручным.

### 8.3 Пять точек расширения (правило роста)

План этого мода не может быть твёрдым: знания о движке пополняются, и механика иногда рождается
раньше плана (ранги 85.56 — пример). Управляемость держится не на плане, а на том, что у каждой
новой идеи есть ровно одна дверь:

1. **новое знание** → атласы и файловая база (`TypeAtlas`/`ActMap`/`EnemyTypes`, `EnemyFileBase.h`)
   — сначала данные, потом код;
2. **новый факт о мире** → канал в `CombatBus` (как `WorldPresence.inCombatAction`);
3. **новое поведение** → модуль с `GetDelta` в оркестраторе (рецепт: `DEV_PLAYBOOK.md`);
4. **новый шаг** → строка в цепочке `UpdatePawnAI` под `__try`;
5. **новая настройка** → ключ ини (живой, без перекомпиляции) + строка в `INI_REFERENCE.md`.

Если идея не помещается ни в одну дверь — это сигнал не «добавить шестую», а пересмотреть замысел.
Правило проверяемое: `tools/module_registry.py` следит за дверями 3–4, `doc_check.py` — за дверью 5,
атласы генерируются, поэтому дверь 1 не гниёт.

### 8.5 ДевТулз остаются

Исследовательский слой (`src/devtools/`, 20% кода) выключен по умолчанию и на продукт не влияет —
это проверяет `tools/analyze_devtools_layers.py`. Соблазн «раз мы давно ничего не искали — вырезать»
понятен, но неправилен: именно этот слой делает план переписываемым. Следующее неизвестное
(новый вид, новый флаг тела, новая таблица) снова потребует инструмента, а не героизма.
Сегодня он не нужен — и это его нормальное состояние: он нужен в день открытия.

Оценка одной строкой: **удобно и грамотно — не по учебнику C++, а по законам своей задачи.**
Это не мод на шине, а reverse-engineering-платформа: три уровня подключения, генерируемые знания
и машинный гейт. Поэтому 45+ итераций не рассыпались в набор фич, а остались управляемыми — в том
числе для смены, которая садится за проект впервые.
