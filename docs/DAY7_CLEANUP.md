## 1. Что было найдено и исправлено

### 1.1. Устаревшее утверждение в документации

`docs/WHAT_WE_HAVE_NOW.md` утверждал, что Act-объект **пересоздаётся** при
переходах. Это опровергнуто дампами: адрес `0x10DC4470` одинаков во всех
пяти снимках (calm / aggro / return / combat / dead). Меняется только
vtable — placement new в стабильном буфере.

Опасность была реальная: на этом утверждении легко построить неверный план
мутаций («ловить момент создания»). Добавлена явная пометка «УТОЧНЕНО» со
ссылкой на актуальные документы.

### 1.2. Мёртвая ветка в `CombatIntel.cpp`

```cpp
if (rva == 0x11E4F34 || rva == 0x11CEF40 || rva == 0x157852C)
```

`0x157852C` — это **VA**, а не RVA. В атласе `uPawnIntel` = VA `0x158CA54`,
RVA `0x117852C`. Сравнение с RVA никогда не срабатывало — пешка не
опознавалась этой веткой.

Исправлено на `0x117852C`, рядом оставлен комментарий с объяснением.

> Проверить в игре: возможно, изменится поведение определения «свой/чужой»
> в CombatIntel. Ветка была мёртвой — теперь она живая, и это стоит
> подтвердить на практике.

### 1.3. Грабли в `ActMap.Generated.h`

Файл выглядит рабочим, но его поле `vtRVA` содержит **factory** vtable и
непригодно для сравнения с живыми объектами (0 совпадений в игре).

Через месяц это гарантированно забудется. В шапку файла добавлен блок
«ВНИМАНИЕ» с объяснением, почему единого сдвига не существует
(дельты разные: гоблин `0x1B1CC`, заяц `0x1B198`) и что работает вместо
этого — имена через DTI.

Имена состояний в файле **верны** и полезны, поэтому файл не удалён.

### 1.4. DevTools по умолчанию выключен

Как договорились. Механика оказалась почти готова:

- флаг `g_enabled` уже существовал;
- `WorldScan_Tick()` уже защищён `if (!g_enabled) return;`.

Изменён только дефолт: `config.getBool("devtools", "enabled", false)`.
Логика «в коде OFF, в нашем ini ON» — правильная: игрок без секции в файле
получает выключённый инструмент, мы у себя оставляем `enabled = on`.

В ini добавлено предупреждение, что это инструмент разработчика и что
скан стоит обхода каждые 150 мс.

## 4. Про сохранение состояний — ответ на твою идею

Ты предложил: держать в оперативке, писать при сохранении игры,
синхронно с ней. **Это правильная модель, и она же стандартная.**

Уточнение только одно, и оно про надёжность:

**Писать в свой файл, а не в сейв игры.** Синхронизировать *момент* записи
с сохранением игры — да, отлично. Но данные класть рядом, например
`ddda_state_<slot>.json`.

Причина: сейв DDDA — чужой формат со своей контрольной суммой. Запись
внутрь означает риск испортить прохождение игрока, а восстановить его
нельзя. Отдельный файл в худшем случае теряется — игрок теряет счётчики
посещений, но не 80 часов игры.

Тонкость с привязкой: если игрок держит несколько слотов, состояние надо
привязывать к слоту, иначе счётчики из одного прохождения протекут в
другое. Простое решение — имя файла по номеру слота.

## 5. Куда дальше: рекомендация

Ты назвал два пути. Уборка заняла один заход и уже сделана, так что
выбор упростился. Мой порядок:

**Сначала — `ddda_entities.ini` с hot-reload.**
Не потому что интереснее, а потому что это множитель: после него каждый
следующий эксперимент (обзор, скорость, поводок) перестаёт требовать
сборки в Visual Studio. Всё, что мы делаем дальше, становится дешевле.

**Потом — пешки.**
Тут есть важный нюанс в твою пользу: инструмент уже умеет всё нужное.
`ProbeSidecars` не привязан к гоблину — он снимает объекты по оффсетам с
любого тела. У `uNpc` подтверждён тот же `+0x2DC8`. То есть препарация
пешки — это **не новая разработка, а прогон существующего инструмента**.

Ожидаемая разница: у пешек есть `rAIPlayerActionParameter` (120 B) и
инклинации, которых нет у врагов. Плюс `sPawnManager` (5512 B).

**Потом — применение параметров в рантайме** (обзор из `.sn2`, темп).

Память спавнов — последней, она требует стабильного слоя 2.

## 6. Честная оценка «мы препарировали большую часть монстров»

Формулировка почти верна, но стоит уточнить границу, чтобы не было
разочарования.

**Что действительно универсально:** карта тела (`+0x2DC0/2DC8/2E64` и
остальные), механизм смены состояния, способ узнать имя через DTI,
формат `.sn2` / `.rst` / `.prp`. Это работает для любого `uEm*`.

**Что специфично для вида:** конкретные Act-классы (у гоблина 139, у
дракона будет своё), значения в файлах, наличие особых подсистем
(варпы у боссов, `cEm5500ActWarp` и подобное).

То есть у нас есть **универсальный метод** и **полные данные по гоблину**.
Для нового монстра это 10 минут работы вместо недели — но не ноль.
