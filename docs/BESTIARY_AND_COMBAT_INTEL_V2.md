# Бестиарий и CombatIntel v2 — как считается знание и бой

## 1. Проценты vs Звезды — плавный vs ступенчатый

**Игра** делает пешку умнее ступенчато, по достижению thresholds из `bestiary.py`:
- 0 звезд: увидел (flag 4160)
- 1 звезда: 60 убийств / 150 сек наблюдения
- 2 звезды: 150-300 убийств + уникальные действия (сбить, поджечь)
- 3 звезды: 300-600 убийств + все уникалки

**Наш SmartUtilitarian** делает плавнее, по битам `mStudyFlag`:
```
bits 0 -> 0.00 unfamiliar 0*
bits 1 -> 0.35  1* но unfamiliar foe (свиток дает 1 бит)
bits 2-3 -> 0.55-0.62 1-2*
bits 4-5 -> 0.80-0.85 2*
bits 6+ -> 0.95 3* familiar
conf = 0.25 + avg*0.65
```
Почему плавнее? Потому что игра дает звезду только после 60 убийств, а пешка уже после 10 убийств чуть-чуть знает что волк боится огня. Наш градуальный конф льет `Utilitarian 800 -> 350` плавно, а не скачком на 3*.

Свиток ставит 1 бит (35%) -> в игре 1* но unfamiliar — мы совпадаем. Твой тест: новая пешка 1* = 35% -> в UI `unk` но уже 1 звезда, 2* = 55% -> тоже unk пока <80%.

Если хочешь строго по звездам — можно переключить на `KillCnt` из `bestiary.py`, но потеряем плавность. Оставляем плавный как ты просил.

## 2. Бандиты vs Волки — починка 0x08 коллизии

До: `targetBase[0x2D]==0x08` для обоих, `FindByGid(0x08)->Wolves` -> бандит = волк.

После фикса (types.tsv vtable):
- `uHumanEnemy vtable 0x15eb494 rva 0x11EB494` занесен в `EnemyTypes.Generated.h` с кастомным `gid 0xE0`
- `BestiaryData.h` + `Bestiary.Generated.h` для id 26/27 теперь `0xE0` вместо `0xFF`
- `CombatIntel::ResolveGid()` в `OnDamage` читает `*(void**)targetBase` и если vtable==human -> возвращает `0xE0` вместо `0x08`
- `GetEnemyCategory(0xE0)-> medium` (1)

Теперь в `Damage Ring Buffer` бандит покажется как `0xE0 Hostile Bandits`, волк как `0x08 Wolves`. Проверь в игре: удар по бандиту больше не пишет Wolves.

## 3. Счетчик убийств — тик под капотом

`g_hitCount[256]` + `g_lastHitTick[256]` throttle 200ms:
- `OnDamage` инкрементит только если прошло >200ms с прошлого хита того же gid
- `g_ring` обновляет timestamp каждый раз (для combat timeout)
- UI показывает `Total hits` и per-gid `hits` — но логика `SmartUtil` и бестиарий тикают каждый кадр через `PublishToBus` плавно.

Т.е. счетчик не спамит, а bus тикает 60fps.

## 4. Укрепление CombatIntel — начало/конец боя

Было: `IsInCombat() = any gid alive <5 sec` -> бой моргал.

Стало:
- `COMBAT_TIMEOUT_SEC 5.0` — для `distinctTypes` (короткое окно)
- `COMBAT_END_HYSTERESIS_SEC 7.0` — для `inCombat` (бой стартует мгновенно на первом `OnDamage`, заканчивается только после 7 сек тишины)
- `PublishToBus` считает `inCombat` с гистерезисом, а `TacticalSwitch` слушает его — пресет не дергается.

Дальше можно усилить: сканировать `sEnemyManager (0x1559bd4) / sHumanEnemyManager` списки живых врагов без урона + проверять `pWorld` combat flag, но пока hysteresis + ring хватает. Это важно для будущего — `TacticalSwitch` и `Nightmare` будут зависеть от стабильного `inCombat`.

## 5. Зайцы = The Dragon — не баг таблицы, 12.08.2026

`FindEnemyByGid(0x61)` → «The Dragon» / family Dragon / категория **5 (босс)**. TSV TypeId `uEm8000` = 97 = `0x61`. Каталог internally согласован.

Dump19: 6 живых тел `[0]=0x015BB278` `+0x2D=0x61`. На экране — 2 стайки зайцев по 3. Цепь из 13 закрыта (4 гоблина + 3 NPC + эти 6). `0x6B` (Hare / `uEm8600`) на цепи нет.

Dump20 (zip 26): `live=10` = 4× `uEm0100` + 6× `uEm8000`. NPC ушли. Kind ярлык = `uEm8000`, не «Dragon». Тот же кластер XYZ, плюс дальний гоблин X=15294.

Dump21 (zip 27): снова 10 = 4+6. Крашей нет. `world.cat=0`. «Пропавшие 3» относительно dump19 — это NPC, не зайцы. TSV `create_uEm8000` — заглушка `return 1`, не конструктор.

Dump22: `meth4_uEm8000` **сам** пишет `[0]=0x015BB278` и `+0x2D=0x61`. Это заводской `uEm8000`, не перепутанный заяц. Бестиарий врёт кличкой, не байтом. По-прежнему не маппить `0x61`.

Поэтому лог пишет Dragon: хук читает живой байт `0x61` и честно идёт в бестиарий. Переименовать `0x61` → Hare нельзя — сломаем Григори. Зайцам титул нравится, потому что паспорт на тушке чужой.

`CombatIntel.cpp` не трогаем. Identity зайца — WorldScan / instance vt, не gid. WorldReport (zip 27) этих шести **не** публикует как Dragon / boss: `KindCategory("uEm8000") = -1`.

Dump24 (zip 30): снова 4+6+3 NPC, `world.cat=0`. Полл закрыт. Лагерные зайцы по-прежнему заводской `uEm8000`.
