# Тест 08 — фантомные реверты и как отличить себя от движка

## Два вывода из присланного лога

### 1. Лог снят с билда 20, не с 21

В логе:

```
EnemyTuner: ForceScale: body+0x60 before=(1.105,1.234,1.261) ...
```

Билд 21 печатает другой формат — с видом и адресом цели, плюс отдельную
строку `ForceScale: цель uEm0100 0x...`:

```
ForceScale: %s 0x%08X +0x60 before=(...)
```

Значит тестировалась старая DLL. И адрес `0x10DD0060` это подтверждает —
это `uEm8000` (заяц), которого билд 21 уже не выбрал бы.

**Следствие:** исправление цели из билда 21 в этом тесте не участвовало.

Чтобы такое больше не повторялось, добавлен `src/BuildTag.h`:
версия печатается первой строкой лога и показана в F12-панели.

### 2. «Реверты» создавали мы сами

```
ForceScale ... wrote=1.000
scale 1.234 ... was=1.000  applies=3 reverts=2
ForceScale ... wrote=0.600
scale 1.234 ... was=0.600  applies=4 reverts=3
```

`was=` — значение, лежавшее в памяти перед записью тика. Там ровно то,
что за мгновение до этого поставила **кнопка**. То есть:

1. кнопка пишет `1.000`;
2. через ≤150 мс `Tick` видит «не моё значение» и пишет `1.234`;
3. `Tick` засчитывает это себе как `revert`.

Движок не откатывал ничего. Счётчик `reverts` измерял конфликт кнопки
с тиком, а не поведение игры.

## Что подтвердилось попутно

Значения в логе — `(1.105, 1.234, 1.261)` — воспроизводятся нашей же
формулой ровно при `scaleJitter = 0.30`:

```
body=0x10DD0060, want=1.234, jitter=0.30
  W = 1.105   H = 1.234   D = 1.261     <- совпадает с логом побайтно
```

Значит работают: чтение ini, hot-reload, `PickScale`, jitter и запись.
Вся цепочка конфига жива. Неизвестно одно — влияет ли `+0x60/64/68`
на отрисовку.

## Что сделано в билде 22

**Режим удержания (HOLD).** `FORCE scale` теперь помечает тело, и `Tick`
его не трогает. Пока висит HOLD, любое изменение значения — дело движка,
а не наше. Это делает диагностику однозначной.

Новые кнопки:

| кнопка | смысл |
|---|---|
| `FORCE scale 0.60/1.00 (hold)` | записать и взять тело под удержание |
| `CHECK hold` | нажать через 2–3 сек: держится ли значение **без нас** |
| `RELEASE hold` | вернуть тело тику |
| `DUMP head 0x00..0x100` | сырые байты головы тела + указатели в ней |
| `LIST enemies + scale` | весь список врагов и их масштабы |

## Зачем DUMP head — сомнение в самой гипотезе

Вывод «`+0x60` = масштаб» держится на одном совпадении: у автора статьи
координаты читались как `[eax+40]`, и у нашего тела `xyz` тоже на `+0x40`.
Отсюда решили, что его «location structure» — это наше тело `uEm*`.

Это может быть неверно. В атласе есть отдельный тип **`uCoord` (240 байт)**.
Вполне возможно, что структура из статьи — именно он, а совпадение `+0x40`
случайно (координаты в начале объекта — обычное дело).

`DUMP head` отвечает на это прямо: печатает `0x00..0x100` как hex и как
float, помечает `+0x40` и `+0x60`, и отдельно перечисляет указатели в
голове с именами классов через DTI. Если настоящая location-структура —
отдельный объект, мы увидим на неё указатель.

## Протокол теста 08

1. Собрать билд 22. **Проверить первую строку лога:** должно быть
   `build 22-scale-truth`. Если нет — собралась не та DLL.
2. Загрузить сейв, `HUNT`, подойти к гоблину.
3. `LIST enemies + scale` → убедиться, что `uEm0100` в списке.
4. `DUMP head 0x00..0x100` → прислать этот кусок лога целиком.
5. `FORCE scale 0.60 (hold)` → посмотреть на гоблина.
6. Подождать 2–3 секунды, `CHECK hold` → прислать строку.
7. `RELEASE hold`.

Три возможных исхода `CHECK hold`:

- **ДЕРЖИТСЯ, модель не изменилась** — движок этими байтами не пользуется
  для отрисовки. Искать множитель в другом объекте (кандидат — `uCoord`).
- **ИЗМЕНЕНО ДВИЖКОМ** — поле живое, но им управляет код игры каждый кадр.
  Нужен хук, а не запись в тике.
- **ДЕРЖИТСЯ, модель изменилась** — победа, включаем через ini.
