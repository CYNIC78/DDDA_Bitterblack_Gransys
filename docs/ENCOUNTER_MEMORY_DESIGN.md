# Память энкаунтеров: телеметрия → мутации

Живой документ. Отвечает на два вопроса: как связать слой среды со слоем
монстров, и почему темп атак должен быть отдельной величиной.

---

## 1. Да, но ключ — не спавн-поинт

Идея верная: писать телеметрию боя, привязывать к месту, следующим боям
в этом месте выдавать поправку к мутациям. Но есть препятствие, которое
`SPAWN_SYSTEM_RECON.md` честно отметил ещё в разведке: **у нас нет
стабильного идентификатора точки спавна**. Классы расстановки
(`cSetInfoEnemy0100` и родня) в атласе есть, живых данных нет, и
неизвестно, переживает ли ID перезагрузку карты.

Ждать этого не нужно. Пространственная память не требует, чтобы движок
делился своей идентичностью:

```text
ключ = хеш(имя карты/зоны, floor(x / cell), floor(z / cell))
```

Ячейка порядка 30–50 метров. Такой ключ стабилен между загрузками по
построению, не зависит от версии игры и не требует ни одного нового
оффсета. Если однажды найдём настоящий ID спавн-точки — сменим ключ,
формат записи не изменится.

Высоту (Y) в ключ не берём: в подземельях этажи наложатся, но лучше
объединить два боя в одной точке карты, чем считать их разными.

## 2. Что записывать

Границы энкаунтера уже есть: трёхсигнальный детектор боя с гистерезисом.
Начало боя — начало записи, конец — фиксация.

| Поле | Откуда | Зачем |
|---|---|---|
| длительность | таймер по детектору | быстро/долго = мера сопротивления |
| враги: сколько и каких | `CombatReport.enemies[]` | сравнивать сопоставимое |
| хиты игрока / пешек | `playerHits` / `pawnHits` | кто нёс бой |
| урон по игроку | CombatIntel (хук урона) | цена победы |
| смерти пешек | детектор `Die/DeadBody` | главный признак перегрузки |
| смерть игрока | флаг | самый весомый сигнал |
| исход | все враги мертвы / игрок ушёл / игрок умер | без него длительность бессмысленна |

Почти всё уже собирается — нужен только сборщик, который сложит это
в запись и положит в свой файл.

## 3. Кривая, а не последний бой

Реагировать на последний энкаунтер — прямой путь к «резинке», которую
игрок чувствует и ненавидит: выиграл легко → следующий бой сразу тяжелее,
проиграл → игра поддалась. Это читается за пару вечеров и обесценивает
победы.

Правила, которые стоит зафиксировать до первой строки кода:

1. **Скользящее среднее по 3–5 последним боям в этой ячейке**, а не
   последний бой.
2. **Малый шаг.** Поправка за один энкаунтер — не больше пары процентов
   к границам диапазона. Изменение должно накапливаться за вечер игры,
   а не за один бой.
3. **Асимметрия в пользу игрока.** Ослабление — быстрее, усиление —
   медленнее. Игрок, у которого не идёт, должен почувствовать облегчение
   раньше, чем игрок в ударе почувствует наказание.
4. **Жёсткий потолок остаётся жёстким.** Никакая кривая не выводит
   множитель за 0.75…1.30.
5. **Затухание со временем.** Место, где не были месяц игрового времени,
   возвращается к базовым значениям.

Проверка на здравость: если игрок замечает адаптацию — она сделана
неправильно. Цель не «подстроить сложность», а сделать так, чтобы
знакомое место не ощущалось решённой задачей.

## 4. Темп атак — да, отдельная величина

Причин три, и каждая самостоятельна.

**Разная цена ошибки.** Скорость перемещения — это где монстр окажется.
Скорость атаки — это попадёт ли удар и успеет ли игрок среагировать.
Вторая напрямую сдвигает окно уворота, то есть трогает боевую честность.
Границы у неё должны быть уже: ориентировочно 0.85…1.15 против 0.75…1.30
у перемещения.

**Разный физический риск.** Перемещение мы уже проверили: движок терпит.
Анимация атаки связана с хитбоксами и событиями в кадрах — слишком
быстрая может не успеть нанести урон, слишком медленная зависнуть.
Это отдельная проверка, а не продолжение предыдущей.

**Разный смысл.** И вот тут появляется приятное следствие: два
независимых множителя на монстра дают четыре характера — бесплатно,
из двух чисел.

| Перемещение | Атака | Что чувствует игрок |
|---|---|---|
| быстро | медленно | налетает, но замах читается — можно наказать |
| медленно | быстро | подкрадывается и бьёт без предупреждения |
| быстро | быстро | берсерк, требует разрыва дистанции |
| медленно | медленно | таран, обходится по кругу |

Это ровно та эмерджентность, за которой мы идём: характеры не
программируются, они возникают из двух чисел, детерминированных от
адреса тела. Гоблин в стае перестаёт быть копией соседа.

Поэтому в конфиге не один диапазон, а два:

```ini
[monsterTempo]
moveMin / moveMax      = 0.85 / 1.15
attackMin / attackMax  = 0.90 / 1.10
```

## 5. Порядок работ

Телеметрия не блокируется поиском темпа атак — это независимые ветки.

1. **Найти поле темпа анимации.** Дифф `cEmActWalk` и полей тела
   (`MONSTER_TEMPO_RECON.md` §3). Без него второй множитель некуда
   применять.
2. **Сборщик энкаунтеров.** Пишет записи в свой файл по границам,
   которые детектор боя уже даёт. Пока без всякого влияния на игру —
   только накопление и просмотр в панели.
3. **Посмотреть на реальные данные.** Прежде чем строить кривую, надо
   увидеть распределение: сколько длится типичный бой, как часто гибнут
   пешки. Настраивать реакцию на выдуманных числах — гарантированный
   промах.
4. **Только потом — поправка к мутациям.** С малым шагом, асимметрией
   и потолком.

## 6. Чего не делаем

- **Не трогаем сейв.** Память живёт в своём файле рядом с модом.
- **Не копим бесконечно.** Ячеек в мире много; храним N последних
  посещённых, остальные забываем.
- **Не показываем игроку цифры.** Внутренняя механика; в панели —
  для нас, в игре — ничего.
