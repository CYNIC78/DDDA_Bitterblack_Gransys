# Правила фиксов дыр (методология вмешательства в AI)

**Зачем:** единые критерии «чиним / не чиним / как». Выкристаллизовано из опыта
проекта (Build 47→63, 19.08.2026).

## 1. Классификация проблемы — ДО любого кода

Каждое «странное» поведение пешки сначала относим к одной из категорий:

```text
(1) ЗАДУМКА (vanilla design)      → пешка ведёт себя так, как Капком и хотели.
                                     НЕ трогаем. Это норма, а не баг.
(2) МЕТА-ЭКСПЛОЙТ                 → «правильно» с точки зрения игрока-оптимизатора,
                                     но противоречит задумке (напр. holy focused bolt).
                                     НЕ трогаем — учить пешку эксплойту = ломать магию.
(3) ДОКАЗАННАЯ ДЫРА               → штатная политика реально ошибается
                                     (напр. Guardian-штраф -3 душит кинжалы).
                                     ВОТ это чиним.
(4) НЕИЗВЕСТНО                    → не хватает фактов. Только read-only наблюдение.
```

**Правило:** пока категория = (4), мы НЕ пишем код. Сначала факты.

## 2. Порядок вмешательства (для категории 3)

```text
offline identity mapped (catalog)
→ live object resolved без абсолютного адреса
→ expected fields validated
→ mutation write
→ readback
→ observable downstream result
→ rollback tested
→ sidecar schema documented
→ vanilla fallback работает
```

Если хоть один пункт отсутствует — это исследовательский probe, а не фича.

## 3. Граница слоёв (что можно/нельзя)

```text
МОЖНО (политика выбора):
    склонности (роль) · приоритет AddS32 · поводок · зона
    eligibility (выбор скилла) — ТОЛЬКО после доказанной дыры (категория 3)

НЕЛЬЗЯ (билд игрока / исполнение):
    вокация · скиллы (набор) · аугменты · характер
    прямая подмена cPlAct / target pointer (ломает FSM/навигацию)
```

## 4. Разбор конкретных примеров (как применять)

| Симптом | Категория | Решение |
|---|---|---|
| Guardian пассивен (не бьёт вблизи) | (3) дыра | снять штраф -3 у code 54, транзакционно ✅ сделано |
| Маг «летит в гущу» | (4)/(3) | сначала поводок (read-only), потом решать |
| Пешка кастует долгие заклинания вместо HFB | (4) | выяснить, есть ли «заряженный core skill» в eligibility пешки |
| Пешка не заряжает focused bolt при снятых скиллах | (4)→(3) | проверить eligibility пешки: легальный приём выпал из её AI-таблицы |
| Огонь против дрейка (без звёзд) | (1) | норма — не знает резистов |
| Огонь против дрейка (со звёздами) | (4) | проверить: связывает ли движок бестиарий с выбором элемента |

### Уточнение категории «мета-эксплойт» (19.08.2026)

HFB (holy focused bolt) — ЛЕГАЛЬНАЯ механика игры: piercing прописан явно, механика
пережила переиздания/патчи. Следовательно это НЕ «мета-эксплойт» (категория 2).
Правильная рамка: разделять
```text
(1) механика легальна в игре?      → да (HFB — да)
(2) есть ли она у ПЕШКИ в арсенале? → вот это вопрос, и это слой eligibility
```

Если приём легален, но пешка его не использует — это ДЫРА В AI ПЕШКИ (категория 3),
а не «учим пешку читу». Проверяется: catalog (есть ли charged core skill в
AIPlActParam, отличается ли для пешки) → live observe (пытается ли пешка зарядить).

Гипотеза пользователя: Капком могли намеренно понизить/запретить charged-атаку
для пешек (оставив метод игроку). Если так — это (1) задумка, не трогаем. Если
нет — (3) дыра, точечный A/B в eligibility.

### Временный градиент по условию (паттерн, 19.08.2026)

Для комбо «Leaping Stone → в полёте → Skull Splitter»:
```text
детект полёта (packed code + current Act) → поднять вес целевого скилла
→ приземление → вернуть вес
```
Это обратимая ситуативная правка, как наш кинжальный градиент (зона → вес).
НО слой другой: вес КОНКРЕТНОГО скилла (skill selection), а не priority (AddS32).
Требует разведки skill-selection слоя (equipped skills +0x868, AIPlActParam CSV).

### Миссия продукта (19.08.2026)

Цель: не должно быть «мусорных» скиллов / аугментов / инклинаций.
- Инклинации → наша зона (доктрина, уже работаем).
- Скиллы → через skill-selection веса (разведка впереди).
- Аугменты → НЕ трогаем (билд, «граница вмешательства»).


## 4б. Readback — не доказательство согласия движка (21.08)

`validate → write → readback → rollback` подтверждает, что **байты легли**.
Он НЕ подтверждает, что игра эти байты читает, и не ловит случай, когда
движок возвращает значение обратно через кадр.

Для правок чужого/живого состояния добавляется пятый шаг:

```text
validate → write → readback → WATCH (2-3 с: держится или откатывается?) → rollback
```

И правило процесса: **проверку выполняет мод, а не человек в игре.** Если
единственный способ узнать результат — сходить посмотреть в интерфейс
игры, инструмент недоделан. Стоило трёх итераций и одного потерянного
A/B-боя (см. `HIRED_PAWNS_SCOPE.md` §11).

И третье: **у записи должен быть голос.** Каждая смена состояния правки
(armed / applied / rolled back / failed) обязана печатать строку в лог.
Guardian-фикс полтора десятка сборок жил со статусом только в панели — и
мог всё это время молча не работать из-за неразрешённого правила; узнали
случайно (`GUARDIAN_REPORTS_MAP.md` §13).

Отдельно: **интерфейс игры может быть невалидным свидетелем.** Профиль
наёмной пешки показывает карточку Рифта и заморожен по устройству игры —
по нему нельзя судить ни о нашей записи, ни о чужой.

## 5. Неподвижные принципы (напоминание)

- не сохранять heap-указатели; не менять DDDA.sav; не угадывать offsets;
- validate → write → readback → convergence → rollback;
- приоритет — «совет», а не приказ; GOAP/FSM исполняют сами;
- F9 не трогать; vanilla fallback при неизвестной версии.

### Уроки разведки (Build 64, серия крашей)

1. **Полный census в активной игре — ЗАПРЕЩЁН.** Проход всей памяти гоняется
   с аллокациями движка → краши. Полный census только для оффлайн/спокойных
   исследовательских прогонов по кнопке.
2. **Точечная разведка — по подтверждённым якорям**, а не по скану. Напр.
   cCmcFollow достижим по цепочке uCmc→cAICtrl→planner→PlanCtrl→node→cCmc
   (6 разыменований, SOURCE_OF_TRUTH §4/§5), каждый под SEH.
3. **Тяжёлую работу не делать на render-потоке** (ImGui-кнопки = D3D9 present).
   Поставить флаг → исполнить на pawn-потоке.
4. **Проба — временный инструмент**: вопрос → ответ → записать в SOURCE_OF_TRUTH
   → удалить кнопку. Знание живёт в доках/артефактах, не в вечном UI.
5. **Продукт не должен зависеть от research-флага** (bug: WorldScan под devtools.enabled).

## 6. Подобъект ищется по ИМЕНИ КЛАССА, а не по смещению

Правило старое (записано в шапке `EnemyTuner.h` ещё в августе), но
нарушается регулярно — стоит увидеть в дампе красивое круглое смещение,
и рука тянется его захардкодить.

Случай 19.08: обход нашёл планировщик пешки на `cAICtrl +0x0068`, я это
смещение зашил в три функции. Следующий же запуск дал
`planner not at cAICtrl+0x68 this time`.

Почему так происходит: часть слотов переиспользуется под разные объекты
в зависимости от состояния. Подтверждённый пример у гоблина:

```
слот +0x2B98:  CALM -> uPlayer      AGGRO -> uCmc
```

**Как правильно:**

1. читать слот по известному смещению можно — но **обязательно сверять
   имя класса** через DTI;
2. не совпало — искать перебором слотов родителя по имени;
3. не нашлось и там — обход вглубь, и только потом отвечать «нет»;
4. фактическое смещение печатать в лог: если оно поменялось, это факт
   для документации, а не повод для отказа.

Так устроен `EnemyTuner::FindCharParam` (сигнатура вместо оффсета) и
теперь `GoapProbe::ResolvePlanner`.

## 7. Охота за адресом — сначала снапшот, не прибор

Кейс, который стоил день (гоблин fakehit, 84.16): волчий блок B
(`+0x274/+0x27C`) уже был каноном. Агент решил, что «на гоблине
раскладка другая» и начал писать новые observe-модули. Сигнал
появился бы на двух дампах одной карты: до удара и после.

**Правило переноса на новый вид / новый статус:**

```text
1. Открыть SOURCE_OF_TRUTH. Есть ли уже якорь того же слоя?
   (карта агра, ряд темпа, слот statusparam, Act +0x2DC8)
2. Если якорь есть — ДВА снапшота существующим прибором
   (EnemyTuner A/B, CARDRECON, snapshot to log, PartyStatus).
   До / после одного ванильного события. Никакой новой .cpp.
3. Дифф только внутри якоря (одна карта, один ряд, окно ±32 B).
   Не «весь uEm*».
4. Не совпало на якоре → один контрольный снапшот (A2, тот же покой).
5. Новый прибор писать ЗАПРЕЩЕНО, пока шаг 2 не сделан и не записан
   в лог как «A/B на якоре X: пусто / вот поле».
6. Сошлась форма, не сошлась запись (флаг не 0/1, другой fC) —
   это гейт вида, не новый слой. Смотри goblin (f8&1, fC=5).
```

Новый `*Observe.cpp` / новая кнопка F12 = признание, что существующий
DUMP не умеет снять два кадра. Если умеет — агент занимается прокрастинацией.
