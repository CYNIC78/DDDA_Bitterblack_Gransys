# Живые классы игрока и главной пешки

**Статус:** подтверждено в рантайме 2026-08-15, build `37-player-pawn-dti-fix`.
**Дампы:** три контролируемых состояния одного запуска: ГГ бежит, ГГ спринтует, ГГ стоит; главная пешка во всех трёх снимках бежит следом.

Это карта **живых сценических объектов**, не записей `pBase`.

---

## 1. Идентичность тел

| Роль | DTI-класс | Размер | Наблюдавшаяся live vtable | Статус |
|---|---|---:|---:|---|
| Воскресший | `uPlayer` | `0x5A10` (23056) | `0x015C9D70` | ✅ DTI + три снимка одного тела |
| Главная пешка | `uCmc` | `0x58E0` (22752) | `0x015C9108` | ✅ DTI + три снимка одного тела |

Абсолютные адреса тел (`0x10D80060`, `0x10D85AC0`) действуют только в конкретном запуске. Идентифицировать тела нужно по DTI, а не по абсолютному адресу или старой vtable.

Старое наблюдение `uPlayer vt = 0x015EFD38` в текущем запуске не встретилось и универсальным адресом не является.

---

## 2. Общий action/FSM layout

У `uPlayer` и `uCmc` совпадает главный участок action-системы:

| Оффсет от live body | Тип | Назначение | Статус |
|---:|---|---|---|
| `+0x2DC0` | ptr | `cActionManager::cActBank` | ✅ DTI |
| `+0x2DC8` | ptr | текущее действие `cPlAct*` | ✅ Run/Dash/Wait на ГГ; Run на пешке |
| `+0x2DE8` | ptr | дубликат указателя текущего действия | ✅ во всех трёх снимках |
| `+0x2E64` | ptr | `cAICtrl` | ✅ DTI; у пешки есть обратная ссылка на body |

### Контрольные состояния

| Состояние | ГГ `uPlayer + 0x2DC8` | Пешка `uCmc + 0x2DC8` |
|---|---|---|
| ГГ бежит | `cPlActRun` | `cPlActRun` |
| ГГ спринтует | `cPlActDash` | `cPlActRun` |
| ГГ стоит | `cPlActWait` | `cPlActRun` |

То, что пешка оставалась в `Run`, дало чистый контроль: её FSM не повторяла смены состояния ГГ.

---

## 3. Act-буфер переиспользуется

У ГГ адрес action-объекта не изменился:

```text
uPlayer + 0x2DC8 -> 0x10D7C940
```

Менялась только vtable внутри того же буфера:

| Действие | live vtable |
|---|---:|
| `cPlActWait` | `0x015C128C` |
| `cPlActRun` | `0x015C131C` |
| `cPlActDash` | `0x015C1364` |

Это тот же placement-new механизм, который ранее подтверждён у гоблина.

У главной пешки аналогично стабилен собственный action-буфер:

```text
uCmc + 0x2DC8 -> 0x10D7D200
```

### Подтверждённые поля action-объекта

| Оффсет от Act | Поле | Наблюдение |
|---:|---|---|
| `+0x00` | vtable | меняется Wait/Run/Dash |
| `+0x44` | owner body | указывает на `uPlayer`/`uCmc` |
| `+0x4C` | motion/resource ptr | меняется вместе с действием |
| `+0x54` | `0xFFFFFFFF` | стабильно в трёх состояниях |
| `+0x58` | owner body | вторая обратная ссылка |

## 4. Кандидаты на сырой режим движения

Ниже только кандидаты. Они **не идут в код**, пока не повторён цикл Wait → Run → Dash.

| Body offset | Wait | Run | Dash | Гипотеза |
|---:|---:|---:|---:|---|
| `+0x2DD4` | `0` | `2` | `5` | сильный кандидат на action enum рядом с current-action region |
| `+0x4AE8` | `2` | `1` | `3` | сильный кандидат на locomotion enum |
| `+0x32D8` | `0` | `2` | `1` | режим/фаза движения |
| `+0x1C94` | `0` | `0` | `1` | кандидат на dash-only flag |
| `+0x4B14` | `1` | `1` | `0` | обратный dash-кандидат |

Для определения «персонаж фактически спринтует» уже можно надёжно читать DTI-имя текущего действия `cPlActDash`. Сырой флаг нужен только как более ранний или дешёвый сигнал.

## 5. Статы и stamina

Точные значения тестового сейва не нашлись простым `int32`/`float` в телах или первых 384 байтах отобранных дочерних объектов:

```text
ГГ:            HP 331 / 498, stamina 600
Главная пешка: HP 327 / 505, stamina 595
```

Подтверждены ссылки на ресурсы:

| Body offset | DTI | Смысл |
|---:|---|---|
| `+0x2710` | `rStatusParam` | ресурс параметров статусов, не текущие HP |
| `+0x34E8...` | `rPlStamina` | таблица правил stamina (`Max`, `Run`, `Dash`, recovery и т.д.), не текущее значение |

Следовательно, текущие HP/stamina нужно искать через `pBase`, health-object или отдельный runtime-компонент. Имена `rPlStamina` уже дают карту правил расхода, но не числовой текущий запас.

## 6. Следующая проверка

Повторить только три состояния ГГ в том же запуске:

```text
Wait -> Run -> Dash
```

Пешку специально заставлять спринтовать не требуется. Повтор нужен для подтверждения кандидатов `+0x2DD4`, `+0x4AE8`, `+0x32D8`, `+0x1C94`, `+0x4B14` на независимом цикле.

Build `39-party-live-trace-hotkeys` делает это автоматически с частотой около 6–7 строк/с. Он одновременно пишет в CSV окна записей `pBase` и первые 32 байта найденных DTI-объектов с именами `Stamina`/`Health`/`Status`. Клавиша `-` рядом с Backspace включает/выключает trace, клавиша `=` делает резервный snapshot. Инструкция тестировщику находится в корневом `BUILD_THIS.txt`.
