# Роль пешки = её стек склонностей (дизайн, до кода)

**Статус:** шаги 1-3 реализованы в `85.12-guardian-role-stack`
(`src/pawnai/PawnPersona.{h,cpp}`, цикл по слотам в `GuardianDoctrineTick`,
телеметрия на пешку). Игрового прогона не было. Полевой порядок -
`docs/GUARDIAN_HARDENING.md`, раздел 85.12.
**Повод:** `docs/PLAYER_PAWN_WORK/GUARDIAN_ENGAGE_RECON.md` §10.2 — доктрина
выбирает «одного гвардиана на партию» первым подходящим слотом, из-за чего
Guardian-логика уходит Страйдеру, а файтер-танк остаётся ни с чем.

---

## 0. От чего отказались и почему

Первый набросок предполагал **арбитра партии**: собрать карточки всех
пешек, сравнить, выбрать одного главного гвардиана. Тестер снял это решение:

> «Мы тут переусложнили. Нам не надо вычислять главного гвардиана среди
> пешек. В пати может быть несколько гвардианов. Всё зависит от стека
> инклинаций конкретной пешки. Обе пешки становятся телохранителями с нашей
> доктриной. Арбитр не нужен — достаточно иметь информацию из стека».

Это верно и упрощает систему радикально:

* **роль — свойство пешки, а не партии.** Никаких сравнений между пешками,
  никакой конкуренции за носителя, никакого гистерезиса владельца;
* **доктрина масштабируется на всех, кто подходит.** Два гвардиана — два
  телохранителя, каждый со своим состоянием;
* исчезает целый класс багов: «кто сегодня главный», «роль мигнула»,
  «главная пешка забрала себе чужое».

Остаётся ровно один вопрос, и он локальный: **эта конкретная пешка —
гвардиан, нексус или никто?**

## 1. Что решает ранг, а не вес

Правило из `cmc.prt` срабатывает по паре `{склонность, ранг}`:

| правило | условие | эффект |
|---|---|---|
| `code 54 WpnDaggerAtk` | Guardian **primary** | `−3` |
| `code 54 WpnDaggerAtk` | Guardian **secondary** | `−2` |
| `code 15 Air` | Guardian / Nexus / Medicant, tertiary | `−2` |
| `code 55 WpnWandAtk` | Nexus **primary** | `−3` |
| `code 55 WpnWandAtk` | Nexus **secondary** | `−2` |
| `code 60 Em0600Cover` | Guardian **primary** | `−3` |
| `code 66` | Guardian **primary** | `−4` |

Канон нумерации: живой ранг **`2 = primary`, `1 = secondary`, `0 = tertiary`**,
ниже — вне стека. В таблице эррат своя нумерация (`0 = primary`) и перевод
`2 - rank` (`PriorityPlatform.cpp:890-892`) — не смешивать.

Отсюда правило сравнения внутри одной пешки и ответ на пример тестера:

```text
пешка A: Guardian 600, ранг 2 (первичная)
пешка B: Guardian 700, ранг 1 (Scather 800 выше)
```

По весу ведёт B. По поведению — **A**: у неё стреляют правила уровня
primary, у B — уровня secondary. Ранг первее веса.

## 2. Персо́на пешки

```text
rG, vG = ранг и значение Guardian в ЭТОМ стеке
rN, vN = ранг и значение Nexus в ЭТОМ стеке

если rG > rN             -> GUARDIAN
если rN > rG             -> NEXUS
если rG == rN и vG > vN  -> GUARDIAN
если rG == rN и vN > vG  -> NEXUS
полное равенство         -> GUARDIAN   (решение тестера; защита важнее связки)
```

Порог годности (тот же для обеих персон):

```text
personaRank  >= 1        // не ниже вторичной
personaValue >= 350      // нынешний порог; ключ ini
тело найдено, координаты санитарны
```

**Почему порог по рангу лечит нынешний баг без правки билда.** Ползунок
главной пешки `guardian = 350` при соседях 750/750/700 даёт ранг «вне
стека» → Страйдер не кандидат вовсе. Файтер с Guardian-первичной проходит.
Ни ползунки, ни запись персонажа трогать не нужно.

Косвенное подтверждение уже в логе: `GuardianLever` молчал именно потому,
что Guardian у страйдера не входил в два верхних (§10.3 того же документа).

## 3. Откуда брать ранг

| источник | вердикт |
|---|---|
| **Считаем сами** из базовых значений (сортировка по убыванию, тай-брейк детерминированный) | **решение принимает этот.** Детерминировано, тестируемо без памяти игры, не зависит от недоказанного поля |
| Живое тело `cCmcInfo + 0x14B8 + id*0x0C`, поле `+0x00` (`0/1/2`), `+0x08` = value (`PAWN_AI_LIVE_BRIDGE_RESULT_40.md` §4) | **диагностика.** Поле названо «context/state», а не «rank»; что игра считает рангом — не доказано |

Как только замер (§7) покажет, что живое поле совпадает с вычисленным,
источник переключается одной константой, вычисленный остаётся fail-closed.

## 4. Базовые значения, а не текущие

Импульсы двигают склонности на время: «Вперёд!» — Scather +300 и
Pioneer +200 на 6 с, «Ко мне!» — Guardian +350, плюс дельты `VocationCordon`
и `PartyRescueProtocol`. Если считать ранг по текущим значениям, команда
«Вперёд!» на шесть секунд поднимет Scather выше Guardian и **сделает
гвардиана штурмовиком** — пешка выпадет из доктрины посреди боя.

**Правило:**

* главная пешка — `PresetManager::GetBaseTarget()` (то, что выставил игрок);
* наёмные — запись персонажа `ReadAllIncl(incl, slot-1)` (её мы не пишем);
* lerp оркестратора и импульсы в расчёт роли не идут.

Импульсы по-прежнему влияют на поведение. Они не влияют на то, кто есть кто.

## 5. Что меняется в коде

### 5.1 `GuardianDoctrineTick()` — цикл по всем пешкам вместо `break`

Сейчас (`GuardianDoctrine.cpp:580-600`):

```cpp
for (int slot = PARTY_MAIN; slot <= PARTY_HIRED2; ++slot) {
    if (!BindGuardianActor(...)) continue;
    foundGuardianSlot = slot;
    break;                       // <-- один носитель на партию
}
```

Становится:

```cpp
for (int slot = PARTY_MAIN; slot <= PARTY_HIRED2; ++slot) {
    if (!BindGuardianActor(s, slot, ...)) continue;   // per-pawn incl/pos/voc
    if (!Persona::IsGuardian(s)) continue;            // стек ЭТОЙ пешки
    GuardianDoctrine& d = s_doctrine[slot];           // СОСТОЯНИЕ НА ПЕШКУ
    GuardianReport r;
    d.Decide(s, r);
    ApplyGuardian(slot, body, r);                     // пин, темп, липкость
}
```

Что переносится из статики в массив на слот:

| было | стало |
|---|---|
| `static GuardianDoctrine d;` | `GuardianDoctrine d[3]` — своя зона и свой гистерезис |
| `static uintptr_t s_lastTarget;` | `lastTarget[3]`, `lastTargetSince[3]` (липкость) |
| темп-оверрайд по одному телу | по каждому своему телу (см. §5.3) |
| метка `[MainPawn]` в логе | метка слота, которого это реально касается |

### 5.2 `NexusDoctrine` — то же самое

**85.14 — первый этап (согласованный объём):** допуск носителя переведён
на ту же карточку базового стека/ранга `PawnPersona`, что и Guardian, с теми
же порогами `guardianMinRank` и `guardianMinIncl`. Наёмные читаются из
своего стека; у главной пешки команды и импульсы не меняют роль.
Первый подходящий melee-Nexus по слотам остаётся **единственным** исполнителем:
назначение партнёра и его состояние пока общие. `SelectAnchorPartner`
сохраняет прежнюю эвристику выбора напарника и аварийное прикрытие,
но исключает из партнёров ВСЕХ годных Guardian, не только первого.

**85.15:** независимое состояние на каждый слот Nexus: закрепление партнёра,
аварийный latch и лог последней цели больше не общие. Два Nexus вправе
выбрать одну третью пешку. Действующие Guardian и Nexus исключаются и из
обычных, и из аварийных партнёров. Когда все три — Nexus (либо два Nexus
и Guardian), доктрина каждого остаётся без напарника и не пишет цель;
игровой ИИ действует сам. Лог сообщает `no eligible partner` один раз
при смене состояния. Панель Nexus сохраняет прежний одиночный статус
совместимости (`GetStatus`); покарточный доступ — `GetStatusFor(slot)`.

### 5.3 Темп: одна строка на тело

`Tempo::SetOverride` обновляет запись на месте, последний писатель за тик
побеждает (`MonsterTempo.h:199-213`). Сегодня в неё пишут четыре модуля;
с несколькими гвардианами претендентов станет больше, но на тело по-прежнему
один. Нужен арбитраж внутри самих доктрин: «если на этом теле уже стоит
оверрайд спасательного протокола или приказа игрока — не перебивать».
Отдельная задача, записана в `GUARDIAN_HARDENING.md` как «tempo общий».

### 5.5 Мощность доктрины по рангу

Первичная, вторичная и третичная склонности **все** влияют на поведение, и
первичная со вторичной взаимодействуют. Значит доктрина не должна быть
бинарной «включена / выключена»: её мощность следует за рангом, а primapу
склонность мы не подавляем — только добавляем поверх.

| ранг Guardian | что получает пешка |
|---|---|
| **2 — primary** | полная доктрина: пин цели + упреждающий периметр 12 м + критический 6 м + темп 1.25 + импульс склонности (только своя пешка) |
| **1 — secondary** | пин цели + упреждающий периметр 10 м + критический 6 м + темп 1.15; импульса склонности нет |
| **0 — tertiary** | только пин цели: «вот твой текущий противник». Ни темпа, ни расширения периметра |

Почему так. Guardian-вторичная при Scather-первичной — это штурмовик, который
ещё и прикрывает. Наша задача — не переделать его в телохранителя, а добавить
немного guardian-поведения поверх того, что уже есть. Отсюда правило:
**мы ничего не отнимаем у первичной склонности, только добавляем.**

Механизм «взаимодействия» в игре не магия, и он нам известен: каждое
правило в `cmc.prt` стреляет по паре `{склонность, ранг}` и вносит свой
`AddS32`; сработавшие правила складываются. Значит суммарный след
характера пешки вычислим: взять девять значений, получить ранги, выбрать
из `docs/PLAYER_PAWN_WORK/generated/cmc_priority_rows.csv` все правила, чья
проверка совпала, и сложить. Это и есть честный ответ на «а как именно
взаимодействуют первичная и вторичная» — и его можно посчитать оффлайн,
без игры:

```bash
python3 tools/inclination_footprint.py --demo
python3 tools/inclination_footprint.py 750 400 500 700 750 350 350 400 250
```

Инструмент печатает стек, персону и все сработавшие правила с их `AddS32`.
На демо-входе видно главное: при Scather-первичной и Guardian-вторичной на
`code 54` стреляют **оба** правила (`+5` и `−2`, итого `+3`) — вот оно,
«взаимодействие». И видно второе: для Файтера (меч и щит) Guardian не даёт
ни одного правила на его оружие — строки 52/53/56 пустые. Значит характер
файтера-гвардиана в приоритетной таблице почти не выражен, и единственные
наши рычаги для него — пин цели и темп, а не правка правил.

### 5.4 Границы остаются

## 6. Свальба на одной цели

Если два гвардиана стоят рядом, «ближайший к Аризену» даст им одну и ту же
цель, и оба побегут в одного гоблина. Естественный разделитель — считать
цель от **самой пешки**, а не от Аризена: у пешек разные позиции, и
ближайший у них, как правило, разный.

Дополнительный дешёвый вариант, если естественного не хватит: мягкий штраф
телу, которое уже держит другой гвардиан (не запрет, а проигрыш при равенстве).
Включается ключом, по умолчанию **off** — сначала проверить, нужна ли.

## 7. Никакого прибора не нужно

Первый набросок требовал observe-прибор `roles dump` на 30 минут игры.
**Это лишнее.** Стек мы и так считаем из значений, которые модуль уже
читает каждый тик (`ReadAllIncl`); отдельный прибор требовался только для
одной цели — проверить, является ли живое поле `state` в
`cCmcInfo+0x14B8` рангом. А это нам не обязательно: ранг считаем сами.

При обнаружении тела печатаем **одну строку на пешку** с девятью
значениями, рассчитанной верхней тройкой и источником данных:

```text
InclStack: [MainPawn][Strider] body 0x... source=anchor reason=discovered top=Nexus>... | Scather=... Medicant=... Mitigator=... Challenger=... Utilitarian=... Guardian=... Nexus=936 Pioneer=... Acquisitor=...
InclStack: [Hired1][Fighter] body 0x... source=hired-live reason=discovered top=Guardian>... | Scather=... Medicant=... Mitigator=... Challenger=... Utilitarian=... Guardian=993 Nexus=... Pioneer=... Acquisitor=...
```

У главной пешки это **сохранённые якоря пользователя** (без кратких
импульсов). Для наёмной отдельный неизменный «базовый» источник у нас не
подтверждён: `hired-live` — снимок девяти текущих значений с её записи,
снятый при обнаружении тела. Нельзя выдавать его за сохранённый базис.
Для эксперимента с ползунками главной пешки строка повторится при изменении
на ≥1; для наёмной, где значения могут дрейфовать сами, только при смене
верхней тройки или изменении ≥25, не чаще раза в 5 с. Плюс прежняя строка
`Roles:` при смене роли/состава. При выходе из геймплея состояние печати
сбрасывается: повторная загрузка сейва снова выдаст один снимок на тело.

Отдельного прибора или новой панели нет: постоянная панель `Party roles`
показывает только роли. Подробные девять значений остаются в логе.

## 10. Чего не делаем

* не выбираем «главного» гвардиана и не сравниваем пешек между собой;
* не пишем склонности наёмным пешкам — только рантайм-советы;
* не двигаем ползунки игрока, чтобы «сделать» пешку гвардианом;
* не ограничиваем число гвардианов в партии;
* не трогаем монстров и аггро — другой слой.
