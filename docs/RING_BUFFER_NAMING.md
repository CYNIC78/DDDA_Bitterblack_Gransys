# Что показывает Damage Ring Buffer и почему были "Target"

## Короткий ответ

**"Target" — это не имя врага. Это признак провала опознания.**

В коде стояло:

```cpp
e ? e->name : (g_ring[i].groupId == 0 ? "Target" : "???")
```

`groupId == 0` означает «резолвер не смог найти владельца удара».
Слово "Target" читалось как имя цели, хотя значит ровно обратное —
мы не знаем, кого бьём. Плохая формулировка маскировала дыру.

Переименовано в **`UNRESOLVED`**. Теперь провал видно как провал.

## Знание пешки тут ни при чём

Это был твой второй вопрос — показывает ли ринг честное имя или
«что помнит пешка». Отвечаю: **имя и знание разведены по разным
колонкам, и так и должно остаться.**

```
[PLR] gid=0xE0 Hostile Soldiers  KNOWN (2s ago)
       ^         ^                ^
       |         |                +-- знание пешки (мониторинг игры)
       |         +------------------- кто это на самом деле (факт)
       +----------------------------- номер в бестиарии
```

Имя обязано быть честным всегда: это наши глаза при отладке. Знание
пешки (`mStudyFlag`) — отдельный игровой параметр, который мы
наблюдаем, но он не должен влиять на то, что видим мы.

Мешать их — значит ослепить себя ровно там, где интереснее всего:
на незнакомых врагах.

## Почему часть бандитов не опозналась

Три причины, по убыванию вероятности:

1. **Резолвер не нашёл владельца.** Хук даёт указатель на структуру
   здоровья, а тело ищется перебором 16 прямых оффсетов и 6 обратных.
   Для части объектов ни один не подошёл -> `gid = 0`.
2. **`gid` не прочитался,** а `uHumanEnemy` отсекался раньше.
3. Удар прошёл по объекту, который телом врага не является
   (щит, часть тела, призванный объект).

Важная деталь: у людей **все три записи бестиария делят один gid**:

```
{ 26, 0xE0, 80, "Hostile Soldiers", "Human", "uHumanEnemy" }
{ 27, 0xE0, 80, "Hostile Bandits",  "Human", "uHumanEnemy" }
{ 49, 0xE0, 84, "Enemy Person",     "Human", "uHumanEnemy" }
```

`FindEnemyByGid(0xE0)` всегда вернёт **первую** — "Hostile Soldiers".
Поэтому бандиты и подписаны солдатами: это не ошибка опознания, а
предел точности gid. Различить их можно только по чему-то помимо
номера — вероятно, по параметрам экипировки или подтипу в теле.
Пока не знаем, чем; отдельная задача.

## Что сделано в билде 33

Ринг теперь **запоминает имя класса от DTI** в момент удара:

```cpp
struct CombatEntry {
    ...
    char kind[24];   // "uHumanEnemy", "uEm0100", "" если не опознали
};
```

`ResolveGidFromEntity(ptr, &body)` отдаёт наружу тело, которое реально
опознал, и с него снимается имя — тем же `NameOfLiveObjectSafe`, что
использует сканер. DTI вызывается **до** взятия `g_lock`: лезть в
чужую память под блокировкой не стоит.

Приоритет отображения:

| условие | показываем | смысл |
|---|---|---|
| нашли в бестиарии | `Hostile Soldiers` | опознали полностью |
| тело есть, в бестиарии нет | `uHumanEnemy` | опознали класс, записи нет |
| тела нет | `UNRESOLVED` | резолвер не сработал |

Средняя строка — новая. Раньше такой случай сваливался в `???` и был
неотличим от полного провала. Теперь видно разницу между «не знаем
кто» и «знаем класс, нет записи в бестиарии».

## Как читать результат следующего теста

- `UNRESOLVED` **исчезли** -> дыра была в имени, опознание работало.
- `UNRESOLVED` **остались** -> резолвер реально не находит тело для
  части ударов. Тогда следующий шаг: логировать сырой `targetPtr` и
  смотреть, что это за объект — скорее всего понадобится новый оффсет
  в списке `priorityOffsets`.
- Появились строки вида `uHumanEnemy` без имени из бестиария ->
  опознание живо, а вот запись в `BestiaryData.h` не находится;
  чинится в таблице.
