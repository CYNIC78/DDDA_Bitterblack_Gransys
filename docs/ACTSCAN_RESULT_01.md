**Короткий ответ: скан отработал правильно, а таблица была неправильная.
Ошибка моя, и это ровно тот капкан, который проект задокументировал в первый день.**

---

## 1. Что показал дамп

```
uEm0100  ptr 0x10DD7320  vt 0x015852A8   actHits 0
uEm8000  ptr 0x10DD0060  vt 0x015BB278   actHits 0   (×5)
```

`actHits = 0` — значит цикл прошёл всё тело (29 КБ), нашёл указатели, но
**ни один из них не совпал с ActMap**. Это не «поле не найдено», это
«эталон для сравнения не тот».

---

## 2. Доказательство

Гоблин, `uEm0100`:

| что | значение |
|---|---|
| в `TypeAtlas` (и, следовательно, в ActMap) | `factoryVtRVA = 0x11A0474` → VA **`0x15A0474`** |
| **живой** объект в памяти, `[0]` | VA **`0x015852A8`** |
| разница | `0x1B1CC` |

Ровно та же история у Act-классов. ActMap хранит **factory vtable**, а в теле
врага лежит указатель на объект с **instance vtable**. Это разные адреса.

### Что подтверждает вывод

`ScanTextWrites` (я его не трогал при чистке — и правильно сделал) поймал в
`.text` 48 записей `mov [obj], imm32`:

```
0x015A0034, 0x015A007C, 0x015A00C4, 0x015A010C ... шаг 0x48
0x015A124C, 0x015A1598, 0x015A15E0 ...           шаг 0x48
```

Шаг **`0x48`** — в точности шаг Act-таблицы гоблина в атласе
(`cEm0100Action 0x15A04B4` → `ActWait 0x15A04FC` → `ActWaitAtck 0x15A0544`, +0x48).
Тот же диапазон, та же решётка, но **сдвинуто**: ни одного точного совпадения
с ActMap (проверил пересечение множеств — 0 из 812).

Это и есть настоящие vtable действий, которые движок пишет в объекты.
Наш список — их «фабричные» двойники.

## 3. Почему я обязан был это предвидеть

В `docs/FIELD_MAP.md` строка 93 и 192 прямым текстом:

> `Слоты TSV FactoryPointer пустые. Instance ищем как dword = factory vtable в секциях exe.`
> `factory vtable из TSV — это vtable фабрики (create_* в [0]). У живых u* — нет.`

И в шапке `DevTools.cpp`, Zip 12:

> `TSV FactoryVtable for uEm0100 is a path string, not a vtable.`

Весь модуль `DeriveInstanceVts` / `ScanDti` / `ScanTextWrites` существует
**именно** затем, чтобы из factory-vtable вывести instance-vtable. Я построил
`ActMap` напрямую из колонки `factoryVtRVA` атласа и не прогнал его через
этот механизм. Скан искал адреса, которых в живой памяти нет.

Хорошая новость: **сам ActScan исправен** — 8 чтений на тело, дешёвый тик,
пустой результат на мёртвом теле, никаких падений. Чинить надо только таблицу.

## 4. Как чинится

Нужен мост `factory VA → instance VA` для Act-классов. Два пути, оба уже
есть в коде:

**(A) Сдвиг блоком.** Если у всех Act-классов одного вида дельта одинаковая
(у `uEm0100` это `0x1B1CC`), достаточно одной поправки на вид. Проверяется
мгновенно: `writes[]` уже содержит 48 живых адресов с шагом `0x48` — их надо
сопоставить с именами по порядку.

**(B) Через `ScanTextWrites` живьём.** Инструмент уже находит эти записи в
`.text`. Нужно связать «адрес записи» → «какой класс её делает» и построить
таблицу в рантайме, без зависимости от атласа.

Путь (A) даёт результат в один заход, (B) надёжнее на будущее.
Начинаем с (A), проверяем на гоблине, при успехе закрепляем (B).
