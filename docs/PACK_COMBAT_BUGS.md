# Два бага, вылезшие на стае из 10 волков

Оба воспроизведены и исправлены. Не техдолг — настоящие дефекты,
которые просто не проявлялись на одиночных целях.

## Баг 1: UNRESOLVED в массовом бою

### Причина: дебаунсер вытеснял сам себя

```cpp
static TargetDebounce g_targetDebounce[16];   // было
g_debounceHead = (g_debounceHead + 1) % 16;   // кольцо
```

Два независимых просчёта:

1. **16 слотов мало.** Каждое существо занимает 1-2 бакета (тело +
   структура здоровья, они в разных `& ~0xFF`). 10 волков = до 20
   бакетов, плюс игрок и пешки. Слотов физически не хватало.
2. **Вытеснение по кольцу, а не по возрасту.** Голова затирала слот
   бойца, по которому только что попали, вместо давно неактивного.

Дальше цепочка: второй суб-тик того же удара (`mHPCurrent` и
`mHPRecoverable` пишутся раздельно) уже не находил свою запись, шёл в
резолвер как новое событие — и часто приносил указатель на
под-структуру, у которой владельца не найти. Отсюда `UNRESOLVED`.

Ключевая деталь: в реальном бою суб-тики разных существ **перемешаны**
(движок считает урон по всем целям в одном кадре), а не идут парами.
Именно поэтому баг не виден на одной цели.

### Симуляция

`/home/user/tcomp/sim/debounce.cpp` — 40 кадров по 24 цели,
суб-тики перемешаны как в игре:

```
СТАРАЯ (кольцо 16): дубликатов просочилось = 960
НОВАЯ  (LRU 64):    дубликатов просочилось = 0
```

### Исправление

- 64 слота вместо 16;
- вытеснение **свободного или самого старого** слота (LRU), не по кругу;
- `RING_SIZE` 32 -> 64: 32 события на 5-секундное окно тоже мало,
  стая прокручивала кольцо за пару секунд и ранние попадания
  вытеснялись раньше таймаута;
- добавлен счётчик `Unresolved: N` в панель — теперь это измеримая
  цифра, а не «иногда проскакивает».

## Баг 2: попадание игрока записано на имя пешки

### Причина: пешка проходила как враг

`IsPartyMember` проверял ровно три vtable RVA:

```cpp
if (rva == 0x11E4F34 || rva == 0x11CEF40 || rva == 0x117852C)
```

Но у пешек **не одна vtable**: `uPawn`, `uPawnIntel`, `uPawnBase`,
плюс наёмные пешки. Тело, чьей vtable в списке нет, проверку проходило
и дальше опознавалось как обычный враг.

То есть это не «имя перепуталось» — это **пешку записывало в цели**.
Ровно та же природа, что у мёртвого `FindByVTable`: захардкоженный
список vtable против живого мира.

### Исправление

Главным путём стало имя класса от DTI:

```cpp
char nm[40];
if (DevTools::NameOfLiveObjectSafe(ptr, nm, sizeof(nm))) {
    if (strstr(nm, "Pawn") || strstr(nm, "uPlayer"))
        return true;              // свой
}
```

Подстрока `"Pawn"` закрывает всё семейство разом, включая типы, о
которых мы ещё не знаем. Старый список RVA оставлен запасным путём —
он дёшев и срабатывает раньше DTI.

## Что проверять в билде 34

1. Стая волков, активный бой втроём: **`Unresolved` должен остаться
   около нуля**. Если растёт — резолвер не находит тело, и тогда
   следующий шаг: логировать сырой `targetPtr` и искать новый оффсет
   для `priorityOffsets`.
2. Имена пешек в ринге **не должны появляться вообще**. Если появятся —
   значит DTI на пешке возвращает имя без подстроки `Pawn`, и надо
   смотреть, какое именно.

## Замечание на будущее

Оба бага — одного класса: **структура данных, рассчитанная на одну
цель, встречает стаю**. Стоит проверить остальные таблицы
фиксированного размера на тот же сценарий:

- `g_lastHitTick[256][2]` — по gid, стае не мешает;
- `WorldReport::units[32]` и `g_act[32]` в сканере — **32 актора**;
  стая из 10 волков + пешки + NPC подходит к границе вплотную.
  Пока не переполнялось, но запас маленький.
