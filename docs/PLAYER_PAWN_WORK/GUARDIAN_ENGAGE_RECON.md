# Гвардиан в арьергарде: почему он там и чем его подтолкнуть

**Build:** `85.06-hot-reload-safe`
**Заявка (тестер, 25.09):** «Когда начинается битва, гвардиан почти всегда
в хвосте / арьергарде. Я чародей, держу дистанцию и кастую издалека. Если
лезу поближе — гвардиан включается: бьёт в щит, тянет внимание на себя,
атакует подошедших вплотную. По идее, с началом боя он должен подтягиваться
к врагам. Позицию диктовать не надо, но дать сигнал «сократи дистанцию с
ближайшим врагом» — попытаться можно».

Документ — разведка до кода. Все ссылки на код даны файлом и строкой, все
утверждения помечены статусом: **CONFIRMED** (есть живое доказательство или
канон), **OBSERVED** (было в логе один раз, не перепроверено),
**HYPOTHESIS** (структурная догадка, проверки не было).

> **§10** — разбор живого лога `85.11-loot-window`, присланного тестером.
> Он подтвердил часть выводов, опроверг одну догадку и вскрыл два бага,

## 1. Симптом в терминах нашего кода

### 1.1 Зона доктрины считается вокруг Аризена — и кастер её сам гасит

`src/pawnai/GuardianDoctrine.h`:

```text
protectionRadius = 12.0f   // м — радиус зоны ответственности
leashDistance    = 18.0f   // м — поводок pawn↔Arisen
hysteresisEnter  = 1.5f    // м
hysteresisExit   = 3.0f
minDwellMs       = 2000
```

`GuardianDoctrine::Decide()` считает расстояния **только от якоря**
(`GuardianDoctrine.cpp:189-219`):

```text
d = |Arisen − threat|
inCriticalPerimeter = d <= meleeR      (6 м)
inPreemptPerimeter  = d <= enterR && threat.targetingArisen   (13.5 м на входе)
```

Аризен-чародей стоит в 20–30 м от врагов. Условие `d <= 13.5 м` не
выполняется ни разу → `zoneEngaged = false` → доктрина **молчит целиком**:

* не пинится цель (`GuardianDoctrine.cpp:600`);
* не даётся темп-рывок (`:604`);
* не двигается ни склонность, ни `AddS32` (`:626`, `:637`).

Это не баг — это следствие модели. Доктрина построена вокруг **оси защиты**
(Аризен ↔ враг). У кастера эта ось по построению длинная, и вся продуктовая
логика живёт на её ближнем конце. Пока Аризен далеко — бой для доктрины не
начался, хотя для мира он идёт полным ходом.

### 1.2 Роль `Protector` по замыслу — «держись у кастера»

`GuardianDoctrine.h:GuardianRoleOf()`:

```text
мили-пешка + кастер-Аризен  ->  GROLE_PROTECTOR
мили-пешка + мили/лучник    ->  GROLE_ASSAULT
```

`GROLE_PROTECTOR` = «телохранитель: держись у кастера, перехватывай, не давай
сблизиться». То есть «пешка в арьергарде» — это **запроектированное
поведение**, а не поломка. Заявка тестера меняет не багфикс, а определение
роли: Protector должен **выдвигаться навстречу**, а не ждать у ноги кастера.
Это важно зафиксировать: правим не «доктрину сломалась», а «доктрина не
покрывает случай кастера на дальней дистанции».

### 1.3 Отдельная находка: порог владения доктриной

`GuardianDoctrine.cpp:547`:

```cpp
if (mainIncl[I_GUARDIAN] >= 350.0f && mainIncl[I_GUARDIAN] >= mainIncl[I_NEXUS])
```

В текущем `ddda_ai_overhaul.ini` ползунок `[customAnchor] guardian = 350.0`,
а `nexus = 350.0`. Значит проверка стоит **ровно на границе**: оркестратор
ведёт значение лерпом (`smooth = 0.10`) и в покое даёт 349.9х. Доктрина при
этом может мигать «владеет / не владеет» между тиками (OBSERVED по коду,
живого лога нет). Плюс `>=` против `nexus` при равных значениях даёт
совпадение каждый тик, а гистерезиса на входе вownership нет.

Отдельный вопрос, который надо измерить: **какой ранг у Guardian в живом
`cCmcInfo`**. Правила приоритета срабатывают по рангу
(`SOURCE_OF_TRUTH.md` §3.3: `rank 2 = primary / 1 = secondary / 0 = tertiary`),
и при ползунках `scather 750 / utilitarian 750 / challenger 700` склонность
`guardian 350` физически не попадает даже в третий ранг. Тогда всё
Guardian-наследие в `cmc.prt` (ведущее: `code 15 Air −2`, `code 13 Recovery −2`)
не работает вовсе, а поведение пешки определяют **цель и eligibility**, а не
склонностные правила. Это ключевой вывод раздела 2.

## 2. Как игра это менеджит: четыре слоя между «вижу врага» и «бегу к врагу»

```text
[1] приоритетный слой   cmc.prt: 85 строк cPrioParam, 48 вёдер,
                        проверки {склонность, ранг}, order-правила
        ↓ выбирается КОД цели (0..90)
[2] цель                uCmc+0x2EB8 (боевая), +0x14E0 (look-at), +0x4B28 (prev)
        ↓
[3] GOAP-план           PlanCtrl(code) = planner + 0x190 + code*0x110
                        внутри — моторные интерфейсы cCmc*
        ↓
[4] eligibility         cCmc* +0x258: шесть float (Range/Enable по XZ и Y)
        ↓
[5] движение            cCmcFollow-поводок + множители Tempo (+0x0EE4..+0x0EF4)
```

| `PL_Party - 06` | 13 | `Recovery` | Nexus −4, Medicant −2, **Guardian −2** (rank 0) |
| `Etc - 04` | 54 | `WpnDaggerAtk` | **Guardian −3 (rank 2), −2 (rank 1)**; Scather +2/+5; Medicant −1 |
| `Etc - 04` | 55 | `WpnWandAtk` | Nexus −3/−2; Scather +2/+5; Medicant −1 |

**Вывод 1.** В приоритетном слое нет ни одного правила «держись сзади».
Guardian штрафует атаку кинжалом, Air, Recovery и пару частных кейсов.
Правил про дистанцию до врага, про «стой у Аризена» и про «не выдвигайся»
в таблице **нет**.

**Вывод 2.** Для Файтера/МК (меч + щит) код 54 неактуален вовсе: его оружие —
`52 WpnSwordAtk`, `53 WpnGSwordAtk`, `56 WpnShieldAtk`. У кодов 52/53/56
personality-правил **ноль** (`cmc_priority_rows.csv`: `Enemy - 05` → 52,

субъективно ничего не менял.

**Вывод 3.** `rAIPriorityThink` — **один ресурс на всех пешек**
(`SOURCE_OF_TRUTH.md` §3.2, Build 75.6). Любая правка `AddS32` действует на
всю партию, включая наёмных. Для «подтолкни одного гвардиана» это
неподходящий рычаг: мы не можем адресовать конкретную пешку, только всех
сразу.

### 2.2 Выбор цели: где рождается «начало боя» для пешки (CONFIRMED)

Живая раскладка кодов за 570 с игры (`generated/pawn_intent_trace_53.json`,

### 2.3 Eligibility: расстояние, с которого действие вообще доступно (CONFIRMED)

У каждого живого `cCmc*` по `+0x258` лежит шестёрка
`RangeMinXZ / RangeMaxXZ / RangeMinY / RangeMaxY / EnableMinXZ / EnableMaxXZ`
в мировых единицах (100 ≈ 1 м). Это **не хитбокс**, а «могу ли я начать это
действие» (`SOURCE_OF_TRUTH.md` §4, `FIELD_MAP.md` §8).

Из `generated/AIPlActParam*.csv` (100 единиц = 1 м):

| оружие | типовой Range | типовой Enable | примечание |
|---|---|---|---|
| Меч | 1.0–2.0 м (36 из 50 строк) | 0 (не задан) | есть строка 0–1.5 м / enable 0–6 м; рывок 4–5 м / enable 3–7 м |
| Щит | 1.0–2.0 м (25 из 29) | 0 | одна строка 1–20 м, одна 0–2 м / enable 0–4 м |
| Кинжал | 1.0–2.0 м (31 из 50) | 0 | одна строка 4–10 м / enable 5–25 м (прыжковый) |
| Лук | **5–15 м** (18 из 38) | **0–20 м** | вот он, «дальний» профиль |
| Посох | 5–10 м | 1–10 м | **мы уже расширяем до 15 / 20 м** — `docs/WAND_RANGE.md` |

Это уже работает и доказано: `WandRange` пишет `RangeMaxXZ = 1500`,
`EnableMaxXZ = 2000` живым `cCmcMagicUserCombo` / `cCmcLightningCloud` / …
и кастеры-пешки начинают кастовать с 15 м вместо 10
(`src/pawnai/WandRange.cpp:446-454`, `PatchSix`). Приёмка живым боем:
`MagickUserCombo` и `LightningCloud` — «APPLIED многократно».

**Отсюда прямой структурный аналог для нашей задачи.** Дальнобойное действие
(лук) имеет Enable до 20 м; ближнее (меч/щит) — ≤ 6 м или не задано. Пока
`Enable/Range` не покрывает расстояние до цели, планировщик **не имеет права
выбрать атаку**, и пешка честно стоит в `Follow`. Мы не «заставляем бежать» —
мы расширяем то же поле, каким уже расширяли посох: «считай это действие
доступным с 15–20 м». Дальше своё дело делает штатный подход внутри `cCmc*`.

## 5. Что предлагаю: вторая ось и «Авто-Вперёд!»

### 5.1 Две оси вместо одной

Сегодня у доктрины одна ось — **Protection** (Аризен ↔ враг). У кастера она
длинная и потому немая. Нужна вторая, независимая — **Engagement**
(пешка ↔ ближайший враг):

```text
Protection axis    d(Arisen, threat)     — «опасность для подопечного»
                   → включает классический режим телохранителя (как сейчас)

Engagement axis    d(pawn, nearestEnemy) — «пешка в контакте или нет»
                   → включает выдвижение на старте боя
```

Они не конфликтуют: **Protection всегда выигрывает**. Как только враг
пересёк зону Аризена (существующее условие), выдвижение снимается и работает
старый, проверенный код. Новый режим нужен ровно в том окне, где старый
молчит: бой идёт, Аризен далеко, пешка стоит.

### 5.2 Минимальный сигнал = рецепт «Вперёд!», только автоматический

На rising edge боя и пока выполняются условия:

1. **Пин** ближайшего живого врага в `uCmc+0x2EB8` и `+0x14E0`
   (то же, что делает `ORDER_GO`, `OrderWatch.cpp:203-205`).
2. **Мягкий подгон** `Tempo::SetOverride(body, 1.15f, 1.10f, 1200)`
   — ниже, чем у приказа игрока (1.25) и ниже потолка 1.30.
3. **Импульс склонности** через `GetDelta`: Pioneer +200 и Scather +150 с
   затуханием 6 с (как `OrderWatch.cpp:120-121`), без записи в сейв и с
   возвратом к ползункам игрока. Pioneer выбран не случайно: в ini про него
   прямо сказано — «грубый рычаг «не липни к якорю»».

Условия включения (всё — чтение, без записи):

```text
бой начался          : DamageRingActive() || enemyCombatCount > 0
                       (НЕ inCombat целиком — см. риск §7.2)
пешка — наша роль    : слот Guardian найден, как в GuardianDoctrineTick
есть кто-то рядом    : d(pawn, nearestEnemy) > engageRadius (порог входа)
не убегаем от Аризена: d(pawn, Arisen) <= tetherRadius
зона Аризена чистая  : !r.zoneEngaged  (иначе правит классика)
```

Условия выхода: вошли в `engageRadius − гистерезис`, открылась зона Аризена,
враг умер/пропал, таймаут выдвижения истёк, бой кончился.

**Чего мы НЕ делаем:** не пишем позицию, не подменяем `cPlAct`, не запускаем
действие, не трогаем планировщик. Мы объявляем «вот твой текущий противник»
и слегка ускоряем шаг — всё остальное игра решает сама. Это ровно тот
принцип, которым сделан приказ «Вперёд!»: единственное отличие — команду
даёт не палец игрока, а детектор боя.

### 5.3 Шаг 2, если пин один не вытянет

Если замер покажет «цель запинена, а пешка стоит» (то есть eligibility не
пускает), тем же механизмом `WandRange` поднять `EnableMaxXZ` у живых
меч/щит `cCmc*` пешки с 0–6 м до 12–20 м. **Range (исполнение) не трогаем**:
удар по-прежнему наносится с 1.5–2 м, меняется только расстояние, с которого
план считает действие доступным, — то есть пешка начинает сближение раньше.
Это структурно то же, что уже принято для посоха, и это не «диктат позиции».

## 7. Риски и предохранители

### 7.1 Конфликт владельцев Tempo
`setOverride` обновляет **одну** строку на тело, последний писатель за тик
побеждает (`MonsterTempo.h:199-213`). Сегодня в неё пишут четыре модуля:
`GuardianDoctrine:604`, `NexusDoctrine:259`, `OrderWatch:205/226`,
`PartyRescueProtocol:176/187`, `PawnHaste:296`. Новый режим — пятый.

**Нужен один хозяин темпа на пешку** (или арбитр «берём максимум»), иначе
выдвижение будет гасить рывок спасения и наоборот. Предлагаю вынести
мини-арбитр в `PawnAI` и им пользоваться, а не городить приоритеты из
порядка вызовов.

### 7.2 Петля через `pawnEngaged`
`pawnEngaged = (uCmc+0x2EB8 != 0)` входит в `IsInCombat()`. Если мы сами
пиним цель, мы **сами держим признак боя** — бой never ends, и выдвижение не
выключится. Поэтому условие старта обязано опираться на
`DamageRingActive() || enemyCombatCount > 0`, а не на `bus.inCombat`
целиком. Записать это в коде комментарием, потому что ошибка будет выглядеть
как «пешка не успокаивается», а не как «мы замкнули петлю».

### 7.3 Порог 350 на границе
`GuardianDoctrine.cpp:547` — `>= 350.0f` при ползунке `350.0`. Нужен ли
гистерезис на вход в владение (например, вход ≥ 340, выход < 300), либо
честно понизить порог. Иначе модуль будет мигать на каждом лерпе.

### 7.4 Наёмные пешки
По `HIRED_PAWNS_SCOPE.md`: только рантайм-советы, запись персонажа чужой
пешки не трогаем. Пин цели и темп — рантайм, допустимы. Импульс склонностей
через `GetDelta` оркестратора идёт **только в главную пешку**
(`g_orch.Tick(incl)` пишет `incl` индекса 0) — это сохраняем как есть.

### 7.5 Цель за стеной / недостижимая
Пин врага, до которого нет пути, = пешка долбится в стену. Ограничители:
`guardianEngageMaxTarget` (30 м), признак «враг живой и в WorldReport»,
таймаут окна, снятие пина при отсутствии сближения за N мс. Пин всегда
снимаем по выходу, никогда не оставляем «до следующего боя».

### 7.6 Откат
Флаг OFF / меню / выход из мира / выгрузка DLL — как у всех транзакционных
правок. Никаких записей в `DDDA.sav`.

### 10.2 БАГ №1: доктрина ведёт главную пешку, а не файтера (CONFIRMED)

```text

   ×27 событий, ВСЕ с меткой [MainPawn], ни одного [Hired1]
```

Причина ровно та, которую заподозрил тестер, и она в коде (85.11,

`BindGuardianActor` (`:546`) требует `guardian >= 350 && guardian >= nexus`

недоступна (нет тела/координат). А когда главная доступна и её Guardian
формально проходит порог, она по-прежнему забирает доктрину себе.

`Guardian` среди ВСЕХ пешек партии (своей и наёмных), с гистерезисом и с
печатью значения в лог. Главная пешка не должна иметь приоритет только за то,
что она главная. Порог 350 при этом превращается из «условия владения» в

### 10.3 БАГ №2: рычаг склонности — доказанный no-op (CONFIRMED)

В логе **ноль** строк `GuardianLever:`. Функция `InclLeverApply()` единственное
место, откуда они печатаются, и она выходит молча ровно в одном месте:

```cpp
if (cur[I_GUARDIAN] <= need) return;     // "уже не первый — не трогаем"
```

То есть `want == true` (зона открыта, пешка melee/hybrid, угрозы есть)
выполнялось многократно, но попытка «опустить Guardian ниже двух соседей»
каждый раз упиралась в то, что **Guardian у главной пешки уже не входит в
два верхних**. Это прямое подтверждение §1.3: склонностной слой в этой
сборке не делает ничего, и чинить в нём нечего.

Косвенное следствие: эррата `E01/E02` (снатие −3/−2 с кинжалов) для **файтера**
бесполезна — её код 54, а у файтера меч и щит. Для Страйдера она осмысленна,
но это не та пешка, которая должна быть Guardian.

*Нумерация рангов (чтобы не споткнуться в замере):* канон
`SOURCE_OF_TRUTH.md` §3.3 — живой ранг `2 = primary, 1 = secondary,
0 = tertiary`; таблица эррат использует свою нумерацию `0 = primary,
1 = secondary` и переводит её как `2 - rank` (`PriorityPlatform.cpp:890-892`).
Две схемы, одно и то же. В лог печатать **живое** значение.

### 10.4 БАГ №3: пин цели дёргается 27 раз за бой (CONFIRMED)

```text
0x11345E60 ×2   0x11135540 ×1   0x11017F90 ×1   0x10D47470 ×1
```

### 10.5 Чего в логе НЕТ, и это главная дыра инструмента

Строка доктрины:

```text
... dist 13.0m (pawn-Arisen 6.7m)
```

`dist` — это `r.nearestThreatDist`, а она считается **от якоря**
(`Decide()`: `nearest = Dist3(anchor, threat)`). То есть в логе
**Аризен → враг**, а не пешка → враг. Расстояния `pawn → враг` нет нигде.

Из лога: `Аризен→враг = 9…13 м`, `пешка→Аризен = 6…14 м`. Значит
`пешка→враг` где-то в коридоре **0…27 м**, и по логу это не определить.
Ровно та величина, ради которой всё затевается, не печатается.

Второму —方位 — тоже нет числа. А заявка теперь сформулирована
позиционно: «быть перед игроком, а не позади». Это считается одной строкой:

```text
dot( (pawn − Arisen), (threat − Arisen) ) > 0   → пешка на стороне врага
```

Оба числа обязаны появиться в логе до любой правки.

### 10.8 Как заявка звучит теперь, и что это меняет в плане

Формулировка тестера:

> «Хотелось бы, чтобы он патрулировал границу своего поводка со стороны
> врагов, то есть был перед игроком, а не позади».

Это **не** «беги к ближайшему врагу». Это «держись на внешней границе
поводка, с той стороны, откуда идёт угроза». Разница принципиальная:

| было в плане (§5) | стало по заявке |
|---|---|
| цель — сократить `pawn→враг` | цель — удерживать `pawn→Arisen` near `leash` **и** `dot(pawn−Arisen, threat−Arisen) > 0` |
| пин ближайшего врага | пин **+ ориентация**: важен не минимум distances, а положение на окружности |
| «не диктуем позицию» | то же, но KPI измерим: доля боевых кадров, где пешка в переднем полукруге |

Практически это означает трёхчастный сигнал вместо одного:

1. **Кто враг** — пин, но липкий (§10.4).
2. **Где граница** — поводок `cCmcFollow` (H1, §10.6): сначала прочитать,
   чем игра удерживает пешку у Аризена, и какова её «дальняя» граница.
3. **В какую сторону** — склонностной импульс в сторону выдвижения
   (Pioneer — штатный ванильный «иди вперёд») плюс мягкий темп, чтобы
   дойти быстрее.

И KPI, который можно мерить автоматически: **доля боевых кадров, в которых
пешка находится в переднем полукруге Аризена (dot > 0) на расстоянии
0.5…1.0 leash**. Сейчас эта доля неизвестна — прибор должен печатать её в
конце боя одной строкой.

### 10.9 Что прошу у тестера перед следующим замером

1. Подтянуть 85.11 в репозиторий (или прислать diff) — иначе правим не тот
   код.
2. Прислать свой `ddda_ai_overhaul.ini` целиком (он отличается от дефолта,

3. Значения склонностей: либо прочитать в игре у файтера и у страйдера

### 10.11 Как читать строку доктрины в логе (шпаргалка)

```text
GuardianDoctrine: [MainPawn] PROACTIVE TARGET -> PREEMPT-INTERCEPT 0x11496780 (uEm0100) dist 13.0m (pawn-Arisen 6.7m)
                  ^кто получил пин            ^уровень              ^тело врага  ^вид     ^Аризен→враг   ^пешка→Аризен
```

* **кто получил пин** — слот-носитель доктрины (`MainPawn` / `Hired1` /
  `Hired2`). Это НЕ «кто в пати гвардиан», а «кого выбрал наш цикл».
* `CRITICAL-MELEE` — враг в 6 м от **Аризена**; `PREEMPT-INTERCEPT` —
  в 12–13.5 м от Аризена и нацелен на него.
* `dist` — **Аризен → выбранный враг** (с 85.09 — именно выбранного, раньше
  мог быть посторонний). Не пешка → враг.
* `pawn-Arisen` — носитель доктрины → Аризен.
* Строка печатается только **при смене тела цели**
  (`s_lastTarget != r.targetThreatBody`), поэтому количество строк ≈
  количество переключений, а не количество тиков.

Чего в строке нет: `пешка → враг`, стороны света (перед/за Аризеном),
имени вокации носителя, значений склонностей. Всё это надо дописать.

### 10.12 Кого отслеживать: решение (ПЕРЕСМОТРЕНО)

Первоначально здесь предлагался вариант C — «выбор носителя по max Guardian
по всей партии». **Тестер его снял:**

> «Мы тут переусложнили. Нам не надо вычислять главного гвардиана среди
> пешек. В пати может быть несколько гвардианов. Всё зависит от стека
> инклинаций конкретной пешки. Обе пешки становятся телохранителями с нашей
> доктриной. Арбитр не нужен — достаточно иметь информацию из стека».

Правильная модель, коротко:

* роль — **свойство стека пешки**, а не партии. Сравнивать пешек между собой
  не нужно вообще;
* годность: `rank(Guardian) >= 1` (не ниже вторичной) **и** `value >= 350`;
* в партии может быть **несколько** гвардианов, каждый со своим состоянием;
* порог по рангу сам убирает Страйдера из кандидатов (`guardian = 350` при
  соседях 750/750/700 → вне стека), правка ini не требуется;
* персо́на при равенстве Guardian/Nexus — **Guardian**.

Полный дизайн: [`docs/PAWN_ROLE_STACK.md`](../PAWN_ROLE_STACK.md).

**Следствие для этого документа:** §10.2 остаётся диагнозом бага, но
«исправление» там было неполным — правится не выбор носителя, а сама модель:
цикл по всем слотам без `break`, состояние доктрины на пешку, а не на модуль.
