# Player + Main Pawn Recon — первый тест

**Сборка:** `37-player-pawn-dti-fix`

**Цель:** найти живые тела Воскресшего и главной пешки, затем прочитать их текущее `cPlAct*`-состояние.

**Безопасность:** инструмент только читает память. Записей в персонажей нет.

## Результат — тест завершён

Build 37 надёжно нашёл ровно два тела по DTI:

- Воскресший: `uPlayer`, size `0x5A10`;
- главная пешка: `uCmc`, size `0x58E0`.

У обоих подтверждён общий current-action slot `body + 0x2DC8`. В сокращённой серии ГГ сменил `cPlActRun → cPlActDash → cPlActWait`, а пешка во всех трёх снимках независимо оставалась в `cPlActRun`. Поэтому заставлять пешку спринтовать больше не требуется.

Простой поиск известных HP/stamina дал `knownValueHits=0`; эти значения не лежат в body/проверенных дочерних объектах как прямые `int32`/`float32`.

Следующий live trace Build 39 закрыл оставшиеся вопросы: `body + 0x2DD4` подтверждён как packed action-code, а current HP/max HP/current stamina найдены в character record `pBase` на `+0x96C/+0x970/+0x978`. Он также поймал прыжок, приземление, урон и автономные оружейные/Lift-действия пешки. Подробности: `PLAYER_PAWN_IN_MEMORY.md` и `PARTY_LIVE_TRACE_RESULT_39.md`.

Описанный ниже пятикадровый протокол сохранён как история первоначального теста; повторять его не нужно.

Контрольные значения тестового сейва уже встроены в снимок как поисковые подсказки:

```text
ГГ:            HP 331 / 498, stamina 600
Главная пешка: HP 327 / 505, stamina 595
```

Инструмент ищет и `int32`, и `float`-представления этих чисел, но совпадение само по себе ещё не считается найденным полем.

Сборка 37 не использует старый жёсткий адрес vtable `0x015EFD38`: он не встретился в текущем запуске. Вместо этого инструмент один раз обходит живые vtable и спрашивает у самой игры их DTI-имена. Ищутся оба ожидаемых больших класса: `uPlayer` (ГГ) и `uCmc` (сильный кандидат на живое тело пешки; в TypeAtlas его размер `0x58E0`, рядом существуют действия `cCmc*`). Поэтому первый поиск может на несколько секунд подвесить F12; следующие снимки F10 используют уже найденные тела.

## Перед тестом

1. Оставить в группе только главную пешку. Наёмных пешек убрать.
2. В `ddda_ai_overhaul.ini` проверить:

```ini
[devtools]
enabled = on

[pawnAI]
enabled = on
```

`pawnAI` должен оставаться включённым только потому, что его 150-мс поток ловит временный хоткей F10.

3. Загрузиться в спокойном месте вне Рифта и большого города.
4. Убедиться, что в F12 сверху написано:

```text
build 37-player-pawn-dti-fix
```

Если написана другая версия — тест не начинать.

## Что нажать

1. Открыть **F12 → DevTools → Player + Main Pawn recon**.
2. Пока ГГ и пешка стоят, нажать **Find both + capture idle** один раз.
3. Должны появиться две короткие строки: `Arisen` и `Main Pawn` либо пока `Candidate A/B`.
4. Закрыть F12.
5. Для каждого состояния удерживать движение и один раз нажимать **F10**:

| Снимок | Что делать |
|---:|---|
| 001 | создаётся кнопкой: оба стоят |
| 002 | ГГ бежит без спринта |
| 003 | ГГ спринтует |
| 004 | остановиться; оба снова стоят |
| 005 | ГГ спринтует достаточно долго, чтобы главная пешка побежала следом; нажать F10, когда пешка явно догоняет |

После каждого F10 в логе должна появиться строка:

```text
PartyRecon: snapshot N bodies=2
```

## Что прислать

Из папки игры:

```text
DDDA_AI_Overhaul\ddda_party_recon_001.json
DDDA_AI_Overhaul\ddda_party_recon_002.json
DDDA_AI_Overhaul\ddda_party_recon_003.json
DDDA_AI_Overhaul\ddda_party_recon_004.json
DDDA_AI_Overhaul\ddda_party_recon_005.json
DDDA_AI_Overhaul\ddda_ai_overhaul.log
```

Самостоятельно разбирать JSON и таблицы байтов не нужно.

## Если инструмент нашёл не две сущности

- `0 bodies`: всё равно будет создан `ddda_party_recon_001.json` с результатом DTI-разведки. Прислать его и лог.
- `1 body`: прислать первый JSON и лог; вероятно, у пешки другой живой класс.
- `3+ bodies`: проверить, что наёмные пешки убраны и тест проходит не в Рифте. Ничего вручную не выбирать — прислать JSON и лог.
- `action not found yet`: это допустимый результат первого прогона. В JSON всё равно сохранены именованные дочерние объекты.

## Что доказывает этот тест

По пяти снимкам проверяем:

1. какие живые классы используются для ГГ и главной пешки (`uPlayer` / `uCmc`);
2. где у них лежат текущие `cPlAct*` / `cCmc*`-состояния;
3. меняется ли состояние `Run → Dash` при спринте;
4. есть ли у пешки отдельный верхний AI-слой (`uPawnIntel`, `cCmc*`, `cAIPlayerActionParameter`);
5. какие байты меняются только во время спринта.

Подтверждённые оффсеты после анализа попадут в `SOURCE_OF_TRUTH.md`. До этого код PawnAI их использовать не будет.
