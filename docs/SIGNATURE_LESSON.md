# MISMATCH — моя ошибка в сигнатуре

Короткая заметка: почему проверка провалилась на правильной структуре
и что из этого следует для всех будущих проверок.

---

## 1. Диагноз

MISMATCH пришёл на том же теле `0x10DD0060`, на котором hex-дамп до этого
успешно показал структуру. Значит дело не в другом виде врага, а в коде.

Проверка требовала три поля:

| поле | ожидал | в памяти | итог |
|---|---|---|---|
| `+0x110` высота смерти | 1500 | 1500 | OK |
| `+0x114` урон % | 50 | 50 | OK |
| **`+0x120` 拘束スローレート Lv1** | 1.0 | **0.0** | **ПРОВАЛ** |

Два поля из трёх совпали. Третье я выбрал неудачно.

`拘束スローレート Lv1/Lv2` — слоу-рейты захвата. В файле они `1.0`, но
движок **обнуляет их в рантайме**: замедление не применяется, пока враг
никого не схватил. Поле живое, значение по умолчанию не сохраняется.

Ирония в том, что данные для этого вывода уже лежали в присланном тобой
hex-дампе — `+0x5990 = 00000000`. Я взял значения из файла, а не из
памяти, хотя память была перед глазами.

---

## 2. Правило, которое из этого следует

**В сигнатуру структуры годятся только поля, которые игра не трогает.**

Как отличить:

| признак | пригодность |
|---|---|
| значение в файле == значение в памяти | ✅ годится |
| движок пересчитывает (таймеры, состояния) | ❌ не годится |
| обнуляется до активации механики | ❌ не годится |

По нашему дампу надёжны: HP `+0x0DC`, камеры `+0x0EC/F4/FC`,
высоты `+0x108…114`, масштаб `+0x12C`.
Ненадёжны: `+0x100` (активация поводка: файл 60, память 30),
`+0x120/124` (слоу-рейты: файл 1.0, память 0).

---

## 3. Что исправлено в билде 16

**Новая сигнатура — три дистанции камер плюс высота смерти:**

```
+0x0EC = 500      ближняя камера
+0x0F4 = 800      средняя
+0x0FC = 1200     дальняя
+0x110 = 1500     высота мгновенной смерти
```

Возрастающая тройка 500/800/1200 — характерный узор, случайно такой в
памяти не встретится. Все четыре поля статичны.

**Добавлен автопоиск базы.** `+0x5870` верен только для `uEm0100`:
у других видов тело другого размера (`uEm0200` 29888, `uEm0500` 29408),
и блок лежит в другом месте. Теперь если по известному оффсету сигнатуры
нет — сканируем тело целиком и сообщаем найденный оффсет.

**Перечисление всех копий.** В теле их минимум две (`+0x5870` и `+0x5900`
по твоему дампу). Логируются все, с их значениями — потому что писать
надо в ту, которую движок реально читает, а какая это, мы пока не знаем.

Проверено симуляцией: обе копии находятся, значения читаются верно.

---

## 4. Что нажать

Та же кнопка **`READ charParam: leash + scale`**.

Ожидаемый вывод:

```
EnemyTuner: body 0x... charParam +0x5870
  return activate (+0x100) = 30    (file: 60.0)
  return duration (+0x104) = 450   (file: 450.0)
  scale           (+0x12C) = 1.0
  copy #0 at body+0x5870: activate=30.0 duration=450.0 scale=1.000
  copy #1 at body+0x5900: activate=30.0 duration=450.0 scale=1.000
  total copies: 2
```

Если копий окажется больше двух — тем лучше, увидим полную картину.

---

## 5. Почему я не считаю это потерей времени

Две ошибки подряд (ложные указатели, потом сигнатура) — но обе поймались
**до записи в память**. Каждая стоила одного теста и дала правило:

1. проверяй, не является ли «указатель» осмысленным float;
2. в сигнатуру бери только поля, которые движок не меняет.

Если бы мы шли сразу на запись, первая ошибка означала бы порчу памяти по
адресу `0x42C80000`, а вторая — тихий отказ работы без объяснения причины.

Это ровно та причина, по которой стоит держать разведку отдельным шагом.
