# Тест 06 — почему масштаб откатился

Результат теста 05 отрицательный, но он дал точную информацию.
Разбираю по шагам, включая мою ошибку в логике.

---

## 1. Что сработало

Сквозной путь **ini → память** работает полностью:

```
ты задал:  scaleMin = 0.7, scaleMax = 0.8
в логе:    scale 0.717 -> body 0x10DD0060 (2 copies)
```

Я пересчитал `PickScale(0x10DD0060, 0.7, 0.8)` — получилось ровно **0.717**.
Значит корректно отработали: чтение ini, кламп, разброс на особь,
поиск структуры, запись в обе копии.

Это первая подтверждённая запись в память игры. Механика доставки готова.

---

## 2. Что не сработало и почему

Значение вернулось к `1.0`. Ключ — **порядок строк в логе**:

```
BaseD3D9 pointer: 00DB031A          <- ранняя инициализация
EnemyTuner: scale 0.717 (2 copies)  <- НАША ЗАПИСЬ (тоже очень рано)
InGameUI enable: MH_OK              <- UI ещё только поднимается
```

Мы записали значение **до того, как игра закончила поднимать сцену**.
Гоблин на тот момент существовал как объект, но его инициализация ещё не
завершилась — и она перезаписала параметры заново из ресурса.

---

## 3. Моя ошибка в логике

Настоящая проблема даже не в тайминге, а в том, что **мы не пробовали
второй раз**.

```cpp
if (AlreadyTouched(body)) return;   // <- вот это
```

Логика была «записал один раз и забыл». Для поля, которое движок может
перезаписать, это неверно: наша запись откатилась, а повторно мы уже
никогда не пытались. Поэтому и после перезапуска игры значение осталось
ванильным — мы писали ровно один раз, в самый неподходящий момент.

**Исправлено в билде 18.** Теперь каждый тик:

1. считаем желаемое значение для этой особи;
2. читаем фактическое из памяти;
3. если расходятся — пишем снова;
4. считаем `applies` (сколько раз применили) и `reverts` (сколько раз
   пришлось переприменять после отката).

Счётчик `reverts` — это диагностика: по нему сразу видно, борется ли
движок с нами и как часто.

Логирование throttled: первые 5 раз, дальше каждый 32-й — чтобы не залить
лог, если откат происходит каждый кадр.

---

## 4. Главный вопрос, который надо закрыть

Возможны два принципиально разных сценария, и они требуют разных решений:

| сценарий | признак | что делать |
|---|---|---|
| **A. Движок откатывает** | `reverts` растёт | писать в момент спавна или найти источник |
| **B. Поле не читается живьём** | значение держится, модель прежняя | масштаб применяется только при создании модели |

Сценарий B вероятнее. Масштаб обычно читается один раз, когда строится
модель и коллизия — менять его у готового объекта бессмысленно, даже если
число в памяти изменится.

### Кнопки для проверки

В билде 18 добавлены две:

- **`FORCE scale 0.60 (write + verify)`** — пишет и **сразу перечитывает**;
- **`FORCE scale 1.00 (restore)`** — вернуть как было.

Вывод в логе будет однозначным:

```
ForceScale: before=1.000 wrote=0.600 copies=2 after=0.600
  -> значение в памяти держится. Если модель не изменилась,
     масштаб читается при спавне.
```

или

```
ForceScale: before=1.000 wrote=0.600 copies=2 after=1.000
  -> значение НЕ удержалось: движок откатывает поле
```

## 5. Что нужно сделать

1. Собрать билд 18.
2. Загрузиться рядом с гоблином, дождаться полной загрузки.
3. Нажать **`FORCE scale 0.60`**, посмотреть на гоблина.
4. Прислать строки `ForceScale:` из лога и сказать, изменился ли он визуально.
5. Нажать `FORCE scale 1.00`, чтобы вернуть.

Заодно, если оставишь `allowWrites = on` и походишь, в логе появятся
строки с `applies=N reverts=M` — это покажет, идёт ли борьба с движком.

---

## 6. Если подтвердится сценарий B

Это не тупик, а уточнение точки вмешательства. Варианты:

**Вариант 1 — писать при спавне.** Нужен момент создания врага.
У нас есть `WorldScan_Tick`, который замечает новых акторов — можно
писать сразу при первом обнаружении тела, до того как модель построена.
Проблема: мы обнаруживаем врага уже готовым.

**Вариант 2 — искать множитель у модели.** Масштаб должен где-то
применяться к `uModel::Joint` (`+0x0364`) или к `cRigidBody` (`+0x1F18`).
Там он живой и меняется в рантайме.

**Вариант 3 — сменить цель.** Масштаб был выбран как самый наглядный
тест, а не как приоритетная фича. Если он упирается в спавн, разумно
переключиться на параметры, которые точно читаются каждый кадр:
таймеры поводка, режим ИИ (`cAICtrl +0x78`).

Я бы предложил **вариант 3** как основной путь и вариант 2 как побочное
исследование. Масштаб — приятный бонус, но не то, ради чего строится
система.

## 7. Честный итог теста

Отрицательный результат, но полезный:

- доставка значений из ini в память **работает и проверена**;
- найдена и исправлена реальная ошибка логики (запись без повтора);
- получен инструмент, который отличает откат от «не читается».

Цена — один тест. Именно так и должна выглядеть отладка записи в чужую
память: маленькими шагами, с проверкой после каждого.
