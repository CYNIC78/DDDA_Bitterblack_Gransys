# Архитектура ИИ: две стороны, одна шина

Состояние на 19.08.2026, сборка `73.4-monster-director`.

## 1. Замысел

Мод строит ИИ **обеих сторон** боя. Пешки учатся помогать осмысленно,
монстры — быть непредсказуемыми. Это не две отдельные поделки: обе
стороны смотрят на один и тот же бой, читают одни и те же данные и
отличаются только выводами.

```
        CombatIntel                 WorldScan
      (кто кого ударил,          (кто в мире, где,
       знание о видах)            что делает сейчас)
             \                        /
              \                      /
               v                    v
                  ==============================
                          CombatBus
                   CombatReport | WorldReport
                  ==============================
                 /                            \
                v                              v
      PawnAI::Orchestrator            MonsterAI::Director
      (сторона союзников)              (сторона врагов)
             |                                |
      инклинации, приоритеты          Runtime::Tempo, EnemyTuner,
      доктрина Guardian               дальше: дистанция, агрессия
```

Ключевое правило: **знание общее, решения раздельные**. Если у сторон
разойдётся картина мира, разбирать «почему пешка видит трёх врагов, а
режиссёр четырёх» придётся в бою, а не в коде.

## 2. Три уровня, и что кому позволено

| Уровень | Кто | Что делает | Что запрещено |
|---|---|---|---|
| **Примитивы** | `Runtime::Tempo`, `EnemyTuner`, хуки движения | применяют числа к конкретной особи, следят за пределами и откатом | знать про бой, про игрока, про фазы |
| **Восприятие** | `WorldScan`, `CombatIntel` → `CombatBus` | собирают факты и публикуют их один раз для всех | принимать решения |
| **Режиссёры** | `PawnAI::Orchestrator`, `MonsterAI::Director` | решают, каким быть бою | писать в память игры напрямую |

Последний запрет — главный. Режиссёр, который сам лезет в память,
однажды промахнётся по «плавающему» слоту и уронит игру. Режиссёр,
который умеет только звать примитивы, в худшем случае примет глупое
решение — а это видно, чинится и не стоит вылета.

## 3. Что уже читается обеими сторонами

`WorldReport` (присутствие, обновляется каждые 150 мс):

| Поле | Смысл |
|---|---|
| `units[].ptr / kind / x,y,z` | кто и где |
| `units[].inCombatAction` | враг в боевом действии |
| `units[].actName` | **имя действия целиком** (`cEm0100ActNAttack1`) |
| `enemyCount / enemyCombatCount / deadCount / critterCount` | состав сцены |
| `dominantCategory` | самая опасная категория |
| `pawnEngaged` | пешка выбрала боевую цель |

`CombatReport` (удары и знание): `inCombat`, `playerHits`, `pawnHits`,
`distinctTypes`, `avgKnowledge01`, `enemies[]` с пометками, кто кого задел.

Поле `actName` добавлено в шину именно ради двусторонности: пешке оно
говорит «гоблин в замахе — можно бить», режиссёру монстров — «правки
темпа сейчас применимы».

## 4. Режиссёр монстров: контракт

```cpp
namespace MonsterAI {
    void Init();            // из InitHooks, до UI
    void Tick();            // из UpdatePawnAI, под своим SEH
    void Shutdown();
    int  ViewCount();       // что он видит — для панели
    const MonsterView* ViewAt(int i);
}
```

`MonsterView` — картина по одной особи: тело, вид, действие, атакует ли,
дистанция до Аризена, итоговые множители темпа и **когда впервые увидели**
(из этого будущие политики берут длительность боя).

Своя частота — 150 мс. Покадровая работа принадлежит примитивам:
режиссёр решает про характер боя, а не про кадр.

### Как политика будет выглядеть

```cpp
static void PolicyEscalation(const MonsterView& v, DWORD now)
{
    if (v.dead) return;
    if (now - v.seenMs < 12000) return;     // бой ещё молодой
    if (v.distM > 15.0f) return;            // не про нас
    Runtime::Tempo::SetOverride(v.body, 1.05f, 1.30f, 5000);
}
```

Правила для любой политики:

1. Решение — по картине боя, а не по одному кадру.
2. Выход — только через примитив, с `ttl`. Бессрочные переопределения
   оставляем состояниям («ранен»), а не всплескам.
3. Всплеск обязан быть **заметен игроку**. Если правила боя изменились,
   игрок должен это понять, иначе он решит, что его просто убили.
4. Никакой политики без отката.

## 5. Чего пока нет и что для этого нужно

| Хочется | Что мешает | Что делать |
|---|---|---|
| доля здоровья монстра | универсального смещения HP в теле не нашли | искать как темп: диф состояния до/после удара |
| кого монстр держит целью | слот `+0x2B98` **плавающий**: в покое `uPlayer`, в агро `uCmc` (`EnemyTuner.h`) | не хардкодить оффсет, а сканировать тело по имени класса; кандидат на отдельную задачу |
| память энкаунтеров | нет хранилища между боями | замысел в `docs/ENCOUNTER_MEMORY_DESIGN.md` |
| разные правила для видов | пока все `uEm*` равны | таблица по `kind`, когда наберётся статистика по видам |

## 6. Замыслы политик (из живых тестов)

### Ярость агонии

Замысел тестера: вести счётчик здоровья **стаи**, и когда он падает ниже
порога — последний бросок. Стая, которой нечего терять, кидается в атаку
«на стероидах».

Почему это хорошая политика, а не просто буст:

- **у неё есть причина**, понятная игроку без интерфейса: враги начинают
  умирать, и оставшиеся звереют;
- **она конечна**: срабатывает один раз за бой и по определению близко
  к его концу;
- **она меняет решение игрока**: добивать по одному больше не безопасно,
  придётся думать о порядке целей.

Что нужно для реализации:

| Нужно | Есть? |
|---|---|
| состав стаи и кто ещё жив | да, `WorldReport` |
| текущее здоровье особи | **нет** — смещение не найдено |
| применить всплеск с откатом | да, `Tempo::SetOverride(..., ttlMs)` |
| телеграфия срыва | нет, отдельная задача (звук/поза) |

### Как найти текущее здоровье

Инструмент уже написан — тот самый, которым нашли темп. Протокол:

1. подойти к целому монстру, `A: normal`;
2. `A2: normal again` (контроль от шума позы);
3. ударить один раз, сразу `B: under the effect`;
4. `Compare`.

Ожидание: поле, которое было около `1000` (значение `human_hp` из
`cCharParamEnemy` у гоблина ровно 1000) и уменьшилось на величину урона.
Оно попадёт во второй список отчёта — «изменения, не похожие на
множитель», потому что фильтр множителей отсекает всё крупнее 16.

Дальше проверка записью: вписать половину — полоска здоровья монстра
обязана уехать на середину.

## 7. Порядок работ

1. **Сейчас**: режиссёр — наблюдатель. Убеждаемся, что он видит бой так
   же, как его видит игрок. Гейт `[monsterAI] enabled = off`.
2. Затем первая политика — эскалация, с телеграфией и откатом.
3. Затем — вторая ручка примитива: дистанция удержания (сейчас монстр
   всегда лезет вплотную).
4. Затем — память энкаунтеров как источник входных данных для политик.
