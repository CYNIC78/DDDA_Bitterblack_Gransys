# Тест 05 — первая настоящая мутация

Билд 17. Разведка закончена, начинаем менять игру.

---

## 1. Что подтвердил твой лог

```
copy #0 at body+0x5870
copy #1 at body+0x59B0
```

Разница `0x59B0 − 0x5870 = 0x140 = 320` — ровно `sizeof(cCharParamEnemy)`.

Это **массив из двух структур подряд**, а не разрозненные копии.
Мой прежний догад про `+0x5900` был неверен: я матчил байты вручную по
куску лога. Автопоиск по сигнатуре нашёл настоящие базы.

Обе копии идентичны: `activate=30, duration=450, scale=1.0`.
**Поэтому пишем в обе** — иначе движок может прочитать нетронутую.

---

## 2. Почему первым делаем размер, а не поводок

Хотя поводок интереснее, размер — правильный выбор для **первой в истории
проекта записи в память игры**:

| критерий | масштаб `+0x12C` | поводок `+0x100` |
|---|---|---|
| видно ли результат | **мгновенно, глазом** | надо бежать и замерять |
| движок перезаписывает? | нет (файл 1.0 == память 1.0) | **да** (файл 60 → память 30) |
| цена ошибки | габарит модели | логика возврата |

Поле поводка движок пересчитывает — наша запись может быть затёрта в
следующем кадре, и мы не поймём, сломалось или просто перезаписалось.
Масштаб статичен, поэтому это чистый эксперимент.

---

## 3. Как устроена запись

**Флаг.** Новый ключ `[global] allowWrites`, **по умолчанию `off`**.
Пока он выключен, мод только читает. Это отдельный флаг от `enabled`:
можно смотреть значения, ничего не трогая.

**Разброс на особь.** Значение берётся из `[scaleMin..scaleMax]`
детерминированно, по адресу тела:

```
body 0x10DD0060 -> 0.918
body 0x10DD7320 -> 0.916
body 0x10DE1000 -> 1.042
body 0x10DF2340 -> 1.124
```

Один и тот же гоблин всегда получает один и тот же размер — не «дышит»
между кадрами. Соседний получает другой.

**Одна запись на особь.** Кольцевой список из 32 тел: если особь уже
получила размер, повторно не трогаем.

**Защита.** `SafeWrite` с `IsBadWritePtr` и SEH-обёрткой. Не пишем, если
там уже наше значение. Не пишем, если `scaleMin == scaleMax == 1.0`.

---

## 4. Что сделать в игре

### Шаг 1 — убедиться, что ничего не сломалось

Собрать билд 17 и просто зайти в игру. `allowWrites = off` по умолчанию,
поэтому поведение должно быть **абсолютно ванильным**.

В логе: `EntityCfg: loaded ... global=on writes=off`.

### Шаг 2 — включить запись

В `DDDA_AI_Overhaul\ddda_entities.ini`:

```ini
[global]
allowWrites = on

[em0100]
scaleMin = 0.85
scaleMax = 1.25
```

Сохранить **не выходя из игры** — hot-reload подхватит.

### Шаг 3 — найти гоблинов

Нужна **группа**, а не одиночка: смысл в том, чтобы увидеть разницу
между особями. Ожидание: гоблины заметно разного роста.

В логе должно появиться:
```
EnemyTuner: scale 0.918 -> body 0x10DD0060 (2 copies)
```

---

## 5. Что может пойти не так, и что это значит

| симптом | вероятная причина |
|---|---|
| в логе есть `scale ... (2 copies)`, но визуально ничего | движок читает масштаб один раз при спавне — надо ловить момент появления |
| размер меняется, но хитбокс прежний | ожидаемо: коллизия отдельно от модели, потому и держим 0.7–1.4 |
| гоблин проваливается в землю | масштаб влияет и на высоту точки опоры — сузим нижнюю границу |
| `(1 copies)` вместо 2 | вторая структура не прошла сигнатуру, стоит прислать лог |
| вылет | немедленно `allowWrites = off`, прислать последние строки лога |

**Самый вероятный исход — третья строка сверху:** масштаб применяется при
создании модели, и живому врагу его смена может ничего не дать. Тогда
переносим применение на момент спавна. Это не провал, а уточнение места.

## 6. Что дальше, если сработает

1. Проверить сигнатуру на других видах (волк `uEm0200`, огр `uEm0500`) —
   у них тело другого размера, автопоиск должен найти базу сам.
2. Поводок: `duration` (+0x104) статичен в отличие от `activate`,
   с него и начнём.
3. Скорость: `cMotionCtrl` пока не найден живьём — искать тем же
   сканером по значению около 1.0.
