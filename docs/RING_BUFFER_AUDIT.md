# Ревизия Damage Ring Buffer

## Вердикт: не вырезать, но чинить

Ринг-буфер и сканер отвечают на **разные вопросы**. Это не дублирование.

| | сканер (WorldScan) | ринг-буфер (CombatIntel) |
|---|---|---|
| вопрос | кто **рядом** | кто **дерётся с нами** |
| источник | обход кучи каждые 150 мс | хук урона, момент удара |
| знает | вид, координаты, состояние | кто ударил: игрок или пешка |
| видит до боя | да | нет |
| различает агрессора | нет | **да** |

Сканер покажет шесть гоблинов у лагеря, но не скажет, что двое уже бьют
твою пешку. Это разная информация.

Плюс `inCombat` реально потребляют два модуля — `SmartUtilitarian`
(строка 20) и `TacticalSwitch` (строка 19). Вырезать = сломать оба.

## Найдено три проблемы

### 1. `FindByVTable` был мёртвым кодом

```
BestiaryData.h  uEm0100 -> vtableRVA 0x11A0474   (ФАБРИЧНАЯ)
живой гоблин    vtable  -> RVA       0x11852A8   (instance)
```

Та же мина, что убила `ActMap::FindByVt`: таблицы из `types.tsv` хранят
factory-vtable, живой объект несёт instance. Совпадений не бывает.

Значит из двух путей опознания в `IsValidEnemyCharacter` работал только
первый — прямое чтение `gid` из `+0x2D`.

**Исправлено:** имя класса через DTI (`NameOfLiveObjectSafe`) +
`FindEnemyByUEmName()` — новый мост «живой объект → бестиарий».
Тот же резолвер, что и у сканера: **обе подсистемы теперь опознают
существ одинаково.** Фабричная vtable оставлена запасным путём.

### 2. Ловушка зайцев добралась и сюда

`uEm8000` в бестиарии числится как **«The Dragon»**, family Dragon,
а `GetEnemyCategory` даёт **категорию 5 = БОСС**.

Лагерные «зайцы» из дампов 19-24 носят именно `gid 0x61` и имя
`uEm8000`. Один удар по такому — и `TacticalSwitch` переключался в
режим драки с Григори.

Переименовать нельзя: настоящий Григори живёт под тем же номером.
**Исправлено:** отсечка по имени класса (`uEm8000`, `uEm8600`) —
единственному признаку, который их различает.

### 3. Fallback приписывал урон случайному врагу

```cpp
// ШАГ 3: Корреляция с активным врагом текущего боя
for (int i = 0; i < RING_SIZE; i++)
    if (свежая запись && groupId != 0)
        return g_ring[i].groupId;   // ЛЮБОЙ gid из боя
```

На смешанной группе это врало: бьём волка рядом с гоблином — урон
записывался гоблину, потому что тот попал в ринг первым.

**Удалено.** «Какой-то враг» хуже, чем «не знаю»: неизвестность видна в
счётчике `unknownTypes` и её можно чинить, тихая подмена — нет.

## Что НЕ трогали

Перебор 16 оффсетов в `ResolveGidFromEntity` (`+0x1B4`, `+0x14`, ...) —
эвристика поиска владельца по структуре здоровья. Работает, заменять
без нужды не стали: сначала надо убедиться, что DTI-путь покрывает
случаи пешек.

## Ответ на вопрос «как работает сканер»

Он **не** ловит момент спавна. Механика такая:

1. `PollSeedSlice` линейно обходит «горячую» кучу
   `0x10000000..0x18000000` порциями по 4 МБ за тик, ища указатель,
   похожий на тело существа;
2. найдя одно тело, `DumpActorsFrom` идёт по связному списку через
   `+0x0C` (next) и `+0x10` (prev) — так за один проход собираются все
   соседи из той же группы;
3. каждые 150 мс список переобходится (`RewalkActors`), данные
   обновляются.

То есть это **периодическая перепись населения**, а не событие спавна.
Отсюда свойства: новый враг появляется в списке с задержкой до
нескольких тиков, а труп висит, пока движок не выгрузит тело.

Надёжность средняя: зависит от того, что тела лежат в известном
диапазоне адресов и связаны списком. Оба факта проверены на дампах
14.08, но это наблюдение, а не гарантия.

**Твоя идея про спавн-поинты правильная и она сильнее.** Если найти
`sSetManager` / `cSetInfoEnemy*` (типы в атласе есть), можно читать
таблицу расстановки: где, кто и при каких условиях появится. Тогда
вместо переписи кучи мы получим карту — заранее и без поллинга.
Это отдельная большая задача, но она того стоит.
