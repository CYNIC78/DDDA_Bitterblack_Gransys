# Разведка: система расстановки врагов (спавн-поинты)

> Восстановлен из истории git (был удалён при чистке документации Build 47).
> Возвращён в дерево 18.08.2026: слой среды — официальное направление
> проекта, см. [`VISION.md`](VISION.md), а это единственная карта входа в него.

Статус: **только разведка по атласу типов.** Ничего не читалось из памяти,
ничего не проверялось в игре. Это карта местности перед выходом, не отчёт.

## Что нашлось в TypeAtlas

Иерархия расстановки в движке выглядит так:

```
rLayout            1144 B   vt 0x1212F40   контейнер расстановки (файл .lot)
 cLayoutSet          64 B   vt 0x118F54C   набор объектов
  cLayoutSetEnemy   152 B   vt 0x118FA10   набор ВРАГОВ
  cLayoutSetEnemyEv 160 B   vt 0x118FA88   набор врагов по событию
  cLayoutSetNpc/Om/Dynamic/CharaBase       остальные наборы

cSetInfo              4 B   vt 0x11CEF40   база записи расстановки
 cSetInfoCoord      112 B   vt 0x1192BE8   запись с координатами
 cSetInfoEnemy      272 B   vt 0x1192D8C   ЗАПИСЬ О ВРАГЕ  <- главное
  cSetInfoEnemy0100 288 B   vt 0x119D0F0   специализация под ГОБЛИНА
  cSetInfoEnemy0101 288 B   vt 0x119D150   ... 0102, 0103
  cSetInfoEnemy8000 288 B                  ... и так на все виды (70 шт.)
 cSetInfoPawn       160 B   vt 0x119353C   расстановка пешек
 cSetInfoSensorTarget

rLayoutGroupParam     584 B  vt 0x12136D8  параметры ГРУППЫ
rLayoutGroupParamList
cExtGroupSetCondition  28 B  vt 0x1154594  УСЛОВИЕ появления группы
rAIDynamicLayout      104 B  vt 0x104684C  динамическая расстановка
cZoneLayout            80 B  vt 0x10357F8  зона
```

Читается это так: **на каждый вид врага заведён свой класс записи
расстановки** — `cSetInfoEnemy0100` это «гоблин в конкретной точке
конкретной карты», 288 байт параметров. Плюс `cExtGroupSetCondition` —
условия, при которых группа вообще появляется.

Именно то, что нужно для «умных спавнов»: точка знает свой вид, свои
параметры и своё условие.

## Чего у нас нет

Файлов расстановки. В `resources/extracted_assets` только гоблин:

```
53 tex, 24 efl, 22 mrl, 19 srq, 19 srd, 13 mod, 7 spc, 5 lmt,
4 ocl, 3 rst, 3 prp, 3 epv, 3 ajp, 2 sn2, 2 ik, 1 stg/shl/rdd/ltg/jex/eap/ean/bmse
```

Ни одного `.lot`. Расстановка лежит в архивах карт (`stage/`), а не в
папке существа — логично, это свойство места, а не монстра.

## Два пути, когда дойдут руки

**Путь А: из памяти.** Найти живой `rLayout` текущей карты, пройти
`cLayoutSetEnemy` -> массив `cSetInfoEnemy*`. Плюс: видим то, что реально
загружено, вместе с состоянием. Минус: надо найти корень.

**Путь Б: из файлов.** Распаковать `.lot` из архивов карт и разобрать
формат — он такой же XFS, как `.prp`/`.sn2`, а с XFS мы уже умеем
(парсер и все грабли описаны в `ASSET_FORMATS.md`). Плюс: видим ВСЮ
карту, включая ещё не загруженное. Минус: статика без состояния.

Скорее всего понадобятся оба: Б даёт карту заранее, А — что живо сейчас.

**Начинать стоит с Б** — там наш готовый XFS-парсер и нет риска
уронить игру, а `cSetInfoEnemy0100` = 288 байт даст сразу проверяемую
гипотезу о размере записи.

## Зачем это нужно (постановка от 14.08)

Спавн-поинт с памятью: помнит прошлые энкаунтеры — длительность,
сложность. На основе этого:

- мутации сидящих на точке монстров (масштаб/поводок уже умеем);
- в пределе — подмена на более сильный вид;
- управление динамикой: не давать игроку скучать и не заваливать.

Это следующий уровень после текущей системы, не вместо неё.

## Важное замечание про vtable

Все RVA выше — **фабричные**, из `types.tsv`. Сравнивать их с живыми
объектами НЕЛЬЗЯ: у живого объекта instance-vtable, единого сдвига нет.
Эта мина уже дважды сработала — `ActMap::FindByVt` и `FindByVTable` в
бестиарии. Для опознания живых объектов — только DTI.

Фабричные адреса годятся для другого: поставить точку останова на
конструктор и поймать момент создания записи расстановки.
