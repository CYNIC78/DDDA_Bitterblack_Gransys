# Замер 2 — слот действия НАЙДЕН

`No ActMap match` — это ожидаемо и не помеха: ActMap собран из factory-vtable
(см. `ACTSCAN_RESULT_01.md`). Полезная нагрузка была в массиве `raw`,
и она сработала.

---

## 1. Главный результат

Сравнение живого и мёртвого гоблина, тело `0x10DD7320`:

```
+2DC8 :  01585654  (живой)  ->  01581A2C  (мёртвый)
```

**Один и тот же оффсет, разные vtable.** Это подпись слота состояния:
объект по адресу меняется, когда меняется поведение.

### Контроль — не совпадение ли это

В сейве было 5 кроликов `uEm8000`. Один из них тоже сменил состояние
между дампами, **и ровно на том же оффсете**:

```
uEm8000 @0x10DF0060   +2DC8 :  015BB5D8  ->  015BB668
```

Два **разных вида** врагов, независимые тела, один и тот же `+0x2DC8`.
Случайностью это быть не может.

Дополнительное подтверждение: у кролика разница между состояниями
`0x015BB668 - 0x015BB5D8 = 0x90 = 2 × 0x48`. **`0x48` — это шаг решётки
Act-классов** (в атласе `ActWait` → `ActWaitAtck` → +0x48). То есть в слоте
лежат именно соседние Act-объекты.

**Вывод: `uEm*+0x2DC8` = указатель на объект текущего действия.**

---

## 2. Что ещё изменилось (и почему это не мешает)

| оффсет | живой | мёртвый | трактовка |
|---|---|---|---|
| `+2AB8` | `0153BD64` | — | объект исчез при смерти |
| `+2B98` | `015C9D70` | — | он же переехал на `+2FA0` |
| **`+2DC8`** | **`01585654`** | **`01581A2C`** | **слот действия** |
| `+2E70` | — | `0157D75C` | появился только у трупа |
| `+2FA0` | — | `015C9D70` | переехавший объект |

Только `+2DC8` **меняет значение на месте** — остальные появляются/исчезают.
Это и отличает «поле состояния» от «объект в списке».

---

## 3. Важное ограничение прошлого замера

`nRaw = 24` у всех тел — это был **мой лимит**, и он исчерпался на `+0x2E64`,
то есть на **40 % тела** (у `uEm0100` тело 29 632 = `+0x73C0`).
Оставшиеся 60 % не просматривались вообще. Лимит поднят до **40**.

Повезло, что слот нашёлся в видимой части.

## 4. Как теперь читаются имена — без атласа

Экстраполировать имя по решётке `0x48` я не стал: проверка дала промах
в 12 байт, а называть состояние «примерно ActRunEnd» бессмысленно.

Вместо этого — **объект сам себя называет**. В MT Framework у каждого
`MtObject` в vtable есть `GetDTI()`, а DTI-карточка в `.data` хранит
`char* name` по смещению `+4` (это уже зафиксировано в шапке `DevTools.cpp`,
Zip 14). Алгоритм:

```
объект -> vtable -> ищем слот вида (B8 imm32 C3) = mov eax, DTI; ret
       -> DTI+4 -> char* -> "cEm0100ActThreatHowl"
```

Никакого TSV, никакого атласа, никаких гипотез о сдвигах — **имя читается
из памяти игры**. Работает для всех 35 видов сразу.

Проверено на симуляции: корректное имя читается; отсутствие `GetDTI`,
не-ASCII мусор и недоступный объект дают честный отказ без падения.

## 5. Что делать с билдом 05

1. Собрать **`builds/05-dti-names.zip`**.
2. Подойти к гоблину, **HUNT**.

Ожидание: возле строки гоблина вместо `raw vt` появится **настоящее имя
состояния** — зелёным, `Die`/`DeadBody` красным, вой жёлтым. В json у каждой
записи `raw` теперь есть поле `"name"`.

Если имена появились — задача закрыта: смерть и таунт читаются напрямую,
и можно пересобирать `ActMap` уже на instance-vtable.

Если `name` пустые — значит `GetDTI` в этой сборке не `B8 imm32 C3`.
Тогда пришли дамп: в `raw` будут адреса vtable, и я подберу сигнатуру
по фактическим байтам.

**Полезно:** если не сложно, снова два состояния (живой + труп). Тогда
сразу увижу пару имён и смогу закрепить категории death/taunt по факту.
